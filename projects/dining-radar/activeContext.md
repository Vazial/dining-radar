## この製品の現在地

`dining-radar` は、**幹事が昼の会を立て、参加者が日程と店を答え、幹事が決める**ところまでを扱う
Web アプリである。公開運用中（Render + Neon、カスタムドメイン。URL はリポジトリに書かれていない
——`adr/0021` の 2026-08-14 追記。実データでの見え方を確かめたいときは人間に開いてもらう）。
`main` へのマージは CI 通過後に Render が自動デプロイする（`render.yaml` の
`autoDeployTrigger: checksPass`）。

プロジェクト名は 2026-08-20 に `toyama-dining-radar` から改名した（`adr/0026`）。公開リポジトリに
実在の県名を持ち込まないため（`product-brief.md` §4・`adr/0002`）。Python パッケージは元から
`dining_radar` で、import・settings・static パス・CSS クラスは動いていない。シナリオ ID の接頭辞
`TDR` もそのまま（承認済み契約を含め 738 箇所に出現するため）。**改名しても公開リポジトリから地域が
消えたわけではない**——`toyama-weekend-radar` と `connpass-session-radar` は今も持っている。

機能の骨格:

- **店を絞る画面**（TDR-CS）: 認証済みの幹事が、徒歩圏・ジャンル・予算・設備で候補を絞り、地図と
  カードで比べる。PC は2カラム（`renderModes.twoColumnLayout`）、スマホは地図主体。
- **会の画面群**（TDR-GTH）: 会の作成、候補日の一括登録（カレンダー複数選択）、参加者への署名付き
  共有リンク配布、日程の3段階回答、店の3段階投票、開催日と店の確定、会の削除。
- **店選びは候補検索画面へ一本化した**（`adr/0049` 決定1）。会モード（`/?gatheringId=<id>`）で
  候補検索画面を開き、カードのトグルで会に入れる/外す。会側に別の店選択画面は**もう無い**。

`product-brief.md` は 2026-08-30（PR #174）で改訂され、会・日程調整・出欠・承認投票を製品境界の
**内側**に入れた。**履歴（過去に行った店の記録）だけは今も境界の外**（§7）——再検討には人の決定と
ADR が要る。

## 未処理の実機フィードバック（2026-09-12、まだ出し切っていない）

公開環境を人間が使って出た指摘。**まだ続きがあると本人が明言している**ので、
**出し切るまで着手しない**（人間の裁定 2026-09-12: 先に全部描かせる／全部出し切ってから）。
出そろったらデザイナーに会の画面群を一通り描かせ、板を見てもらってから実装する。

**描き直しの進め方（人間の裁定、2026-09-12 チャット選択肢UI）**:
- **会が進む順に5つの束へ分ける**——「作る」「日程を聞く」「店を選ぶ」「投票」「確定」。
  各束で幹事の画面と参加者の画面が対で出る。**流れが考えられていないという不満に直接効く軸**を選んだ。
- **1束ごとに止め、人間の反応をもらってから次を描く。**後ろの束に前の裁定が反映される。
- **1束の板は少なく保つ。**「何枚も長い画面を並べられたらレビューできない」。前回の6枚を1つの
  キャンバスに並べた形は不可。
- **画面のつながり（どこから来て、どこへ戻るか）の全体図を第1束に入れる**（FR-036）。
  これが無いと「作る」が全体のどこに置かれているか判断できない。
- 第1束は4枚（読みかた／つながりの全体図／会の入口／会をつくる）。**2026-09-12 に着手。**

### 店を絞る画面（第1便、2026-09-12）

1. 「もう一度探す」というラベルが動作を説明していない。中身は「別の候補を出す」である。
2. 定休日の記載が見にくい（カード末尾で詳細リンクと横並び）。
3. **徒歩◯分が実態に合っていない。**人間が Google の計測を添付（道なり650m＝10分、つまり65m/分）。
   現行は直線距離×1.3÷80m/分の切り上げ。**1点では速度と迂回係数のどちらがずれているか切り分け
   できない**ため、アプリの表示値と Google の値の対を1件もらう必要がある。
   なお**道なりの正確な距離を出すには経路検索サービスへ問い合わせることになり、私的な出発地点を
   外部へ渡すことになる**——この製品の方針で禁じているので、無料の選択肢ではない。
4. 「会」の表現と導線が相変わらず分からない。ヘッダーは絵文字1個＋「会」の一文字で、
   **スマホ幅ではその一文字も `display: none` で消える**。初見の人に伝わる情報がゼロ。

### 会の画面群（第2便、2026-09-12）

5. **会をつくる画面から戻るすべがない。**「ページの構成がそもそも考えられていない」（FR-036）。
6. **会をつくるカレンダーが選べたものではない。**一度もデザインしていない。ライブラリの既定の
   見た目のまま出した。
7. **なぜ3か月表示なのか。**テストを通すための選択だった（FR-033）。
8. リンク発行はよいが、**結果の出し方がいまいち。**誰が何を答えたのか、その結果候補がどうなるのかが
   読めないレイアウト。誰が何を答えたかを一覧する画面はそもそも存在しない。
9. **参加者画面の「あとで答える」「結果をのぞく」のレイアウトが崩れている**（FR-034。確認文が
   同じ flex 行に兄弟として入りボタンが縦一列に潰れる）。
10. 「ここまでの回答…」の一文は要るのか。
11. **店を選んだあとに確定・戻るフローが無い**ので、手で開き直すことになる（FR-036）。
12. **確定後の画面が1行足しただけで分かりにくい。**これは 2026-09-09 の D1（確定後は決定内容を
    見せて終わり）の結果だが、実物を見て違うと判断されたものとして扱う。
13. 確定後の参加者向けリンクでは**店がどこにあるかも見せたい**。
14. 「この日に開いている店 N件」はなぜ書いているのか。
15. **承認を得るための説明文を本番画面に埋め込むのをやめる**（FR-034）。名指しされたのは
    「ほかの人の回答も見えています」「ここまでの回答は保存されています…」
    「幹事から届いたリンクで開いています…」の3つ。

### 第1束「作る」の裁定（2026-09-12、チャット選択肢UI）

デザイナーの板: つながりの全体図・会の入口・会をつくる（`E:\AWS\dsg-out\party1-create\`）と、
カレンダーの見た目3案（同 `b1-calendar-looks\`）。**第1束は決着した。**

- **上部の居場所を2つ常設する**（「ランチ候補をさがす」「ランチ会」）。いまは会に入ると出られない。
  スマホでも文字を消さず、短くする。
- **会をつくった直後は、つくった会へ行く。**そのまま回答リンクを配る作業へ繋がる。
- **候補日ごとの時刻は触らせない。**全部 12:00 から。画面に1回だけ書く。
- **カレンダーは案B（表）。**升目を仕切り、土日に地色を敷いて週の切れ目が形で分かる。
  これを選んだことで、デザイナーが残していた判断4件も同時に決まった——土日に地色を敷く／
  見ていない月の日は一覧で地色を変える／連続した日は粒で見せる（帯にしない）／月送りは上に置く。
- **カレンダーの中身は自前で書く。ライブラリを使わない。**実際に手で書いたものを人間が押して
  「いい感じ」と判断したうえでの決定である。**これで消える問題が2つある**——
  ライブラリが入力欄を必ず作る問題（購入可能な操作の宣言検査に引っかかる）と、
  その回避の副作用で年が月送りで更新されない問題。vendoring している flatpickr 68KB は外せる。
- **範囲選択を入れる**（人間の要望、2026-09-12）。押したまま動かすと範囲、選んでいる日から
  始めるとその範囲が外れる、Shift＋押下でも範囲。1日ずつの選択はそのまま残す。

**実装時に必ず実測すること**: 案Bのマスは**高さ46px**で下限44pxまで2pxしかない。
枠線1pxを当たり判定の外に数える作りにすると割る。

**契約に要素が足りない（architect へ、デザイナーからの申し送り）**:
1. **月送りの2つの矢印**が `allowedPurposes` に無い。**いまの「年が更新されない」不具合は、
   これが宣言されていないことの副作用**である。
2. **選んだ日の一覧の「×」**が無い。これが無いと、見えていない月に選んだ日を外せない。
3. **会モードの候補画面から会へ戻る要素**が無い（`product-brief.md` §2 は要求している）。
4. 「戻る」を2か所に置くと1つの test id が2要素になる（1 test id＝1観測面の原則）。
   板では左上の1つだけにしてある。

### 第2束「日程を聞く」の裁定（2026-09-12、チャット選択肢UI）

デザイナーの板: `E:/AWS/dsg-out/party/b2-schedule/`。幹事の画面は3つに分かれていたパネル
（集計・誰が答えたか・発行済みリンク）をやめ、**1つの表**にした——行が人、列が候補日、
マスがその人のその日への答え。横に読めば1人の答え、縦に読めば1日の集まり。

- **幹事に「誰が、どの候補日に、何と答えたか」を見せる。**いままで見えていたのは人数だけだった。
  **これは製品の境界を動かす決定である**——個人の答えが幹事に開かれる。名前は任意なので
  名無しの行が混ざる。`product-brief.md` §5・§7 の改訂と ADR が要る。
- **参加者の画面から「この日に開いている店 N件」を消す。**2026-08-30 の D6（回答の有無に
  よらず件数だけ出す）を覆す。幹事側には残す——ただし候補日ごとの常時表示はやめ、
  仮に選んだ1日ぶんだけを「この日にする」と同じ帯に置く。
- **「あとで答える」の確認は、文のかわりに今までの答えそのものを並べる。**契約は
  「保存されている」旨の文を要求しているが、それは人間が消せと言った承認向けの文の1つ。
  残っていることを文ではなく実物で示す。
- **「取り消す」は未回答の行にだけ置く。**契約の `revoke.disabledState`（全行に無効状態で置く）
  を覆す。
- **潰れていた2つのボタンは、同じ行に置くのをやめた**——「結果をのぞく」は画面の上、
  「あとで答える」は一番下、確認は重なる別の面。**構造的に同じ崩れが起きない形**にした。
- 分母2種類は表の構造で分けた。未回答の人数は**行の本数**、票の分母は表の足元に1回だけ。

**契約に足りない要素（第2束で新たに判明した分。architect へ）**:
1. **最大の不足: 「誰が、どの候補日に、何と答えたか」を運ぶ道が無い。**幹事が受け取れるのは
   候補日ごとの人数（`CandidateDate.goingCount` ほか）と、リンクごとの `ParticipantLinkSummary`
   （`id`・`issuedAt`・`hasResponded`・`revoked`・`displayName`）だけで、**その2つを結ぶ値が
   API にも観測面にも存在しない**（orchestrator が契約を読んで確認済み）。表の中身が作れない。
2. **候補日を消す操作が無い。**足せる（`addCandidateDates`）が取り除けない。
3. 会から一覧へ戻る要素が無い。

**実装時に実測すること（デザイナーは未実測と明言）**: スマホの表に日付列が2本入るか／
「みんな」の印が12人まで並ぶか／「結果をのぞく」の1件62pxで4件が同時に入るか。

### 第3束「店を選ぶ」の裁定（2026-09-12、チャット選択肢UI）

デザイナーの板: `E:/AWS/dsg-out/party/b3-shops/`。**板は1枚ずつ送って見る形で渡すこと**——
人間の指示「ページングしてみやすい大きさにしてほしい」。キャンバスに全部並べる形は不可。
送り付きページの作り方は `scratchpad/pager/build_pager.py`（板の CSS を shadow root に閉じ、
画面幅に合わせて縮小、矢印キーで送る）。

- **戻る導線と「選び終わった」の合図を1つにまとめた。**店は押した瞬間に保存されるので、
  あとから押す「確定」は「押し忘れたら消える」という嘘になる。置くのは戻る道1本だけで、
  それが件数で顔を変える（0件＝白枠／1〜4件＝「3件を入れて会にもどる」／5件＝地色が変わる）。
  **数が読めること自体が合図**である。
- **「この5件で投票を始める」操作は置かない。**店を1件入れた瞬間に参加者が答えられる。
  幹事が選び途中のものに票が入り始めることを引き受ける。
- **幹事が票を見る画面に地図と店の情報を出す。**人間が板3を見て「ぱっと見違和感ない」と判断。
  **契約の側を直す**——`shortlistedShopVotes` は「地図も店のページのリンクも足さない」（2026-09-05）
  と定めており、`product-brief.md` §2・§3（2026-09-04、`adr/0044`、人間の実機フィードバック）と
  正面から食い違っていた。**説明書が正、契約が誤り**として解消する。
  レイアウトは地図1枚（行番号＝ピン番号）＋1行4項目（名前・徒歩の目安・票の内訳・店のページへの線）。
  席数・禁煙・予算・定休日は出さない（選ぶときに見たものの2回目の印刷になる）。
- **入れ換えた店の印は「あとから入りました」。**参加者にも幹事にも同じ言葉で通す。
- **帯の日付は「9/17（木）」。**曜日を残す（店の定休日の話なので曜日が要る）。
- **スマホでは件数の帯を画面の上に貼り付ける。**地図の高さは減る。**実測すること。**
- 通常の使い方を邪魔しないため、会モードで**足すのは2つだけ、変えるのは0**——帯1本と
  カードのいちばん下の1行。絞り込み・チップ・もう一度探す・地図の輪と基点・カードの項目は無変更。
  「その日に開いている店」は外せない条件なので、外せるチップの列に混ぜず帯の中へ。

**契約に足りない要素（第3束で判明した分。architect へ）**:
1. **会へ戻る要素が1つも無い**（`gatheringMode` の観測面は帯とカードのトグルだけ）。第1束から未解消。
2. 地図のピンに会へ入れた状態を表す属性が無い（カードの `data-gathering-shortlisted` に相当するものが無い）。
3. `gathering-shortlisted-shop-item` は票と `data-shop-id`・`data-current-leader` だけで、**名前を機械で見ていない**。
4. 「あとから入りました」を示す面が無い。
5. 5件に達した理由を言う要素が無い。
6. 会モードのときの `candidate-gathering-entry` の振る舞いが未定義。

**実装時に実測すること**: スマホで上を2段取ったあと地図とカードに何が残るか／PC 左カラムに
カードが何枚入るか／カードの「この会に入れる」48px と地図のピン 44px が枠線の数え方で割れないか。

### 第4束「投票」の裁定（2026-09-12、チャット選択肢UI）

デザイナーの板: `E:/AWS/dsg-out/party/b4-vote/`。送り付きページ: `scratchpad/pager/b4.html`。

- **強調2種は、色・形・場所を同時に変えて見分けさせる。**票の1位＝深緑（「行きたい」の帯と同じ色）
  で行の内側を淡く塗り左端に縦棒／幹事が選んでいる店＝濃墨で行の外周を囲み、右側と下のボタンで言う。
  **緑がいちばん長い店に緑の印**なので、印の意味を説明せずに読める。色は1つも足していない。
- **0票のうちは最有力の印を出さない。**契約は先頭1件を無条件に最有力（`data-current-leader`）に
  するので、店を入れた瞬間に「誰も答えていないのに票がいちばん多い」が出る。**画面が嘘をつく。**
  契約を直す。
- **同票のときは同票の店すべてに印を付ける。**契約は機械的に1件へ割るが、同票なら同じ扱いが正しい。
- **確定に確認を一段置く。**会の削除には2段階あるのに確定には無かった。確定は元に戻せず、
  参加者全員の画面が変わる——削除と同じ重さの操作である。
- **参加者に会の総人数を届ける。**票の帯を「全員の人数」で固定し、票の薄い店が帯の短さで分かるように
  する。**いまの契約では参加者に総人数が届かない**——店ごとの `respondedParticipantCount`
  （その店に答えた人数）はあるが、会全体の人数を運ぶ道が無い（orchestrator が契約を読んで確認済み）。
- **参加者に「あなたの回答」の一覧は作らない。**押したボタンが塗られたまま残ることが一覧そのもの。
  足すと2回目の印刷になり、人間が確定後の画面で「別に意味ないかも」と評したものが投票中に生える。
- **「あとから入りました」は幹事・参加者で同じ言葉。**印は2つに分ける——札は「あとから入ったか」
  だけ、カードの縁は「自分が答えたか」だけ。1つの印に2つの意味を持たせない。

**契約に足りない要素（第4束で判明した分。architect へ）**:

## 確定ポリシー

- 実在の生活圏名・座標・設定した範囲・API キー・秘密・provider のリクエスト URL / レスポンス・
  店 ID・画像・店データ・実データ移行・fixture・DB ダンプを**コミットしない**。合成データのみ使う。
- provider のレスポンスを**キャッシュ・永続化しない**。恒久的な provider ID や HMAC 由来の照合
  データも使わない。これを開け直すには新しい人間の決定・provider 規約の再確認・ADR が要る
  （`adr/0018` は両方を検討したうえで `提案中` のまま）。
- API キーはサーバから provider へだけ送る。キーを含む URL・provider の内部・私的な基点を、
  ブラウザ・公開 URL・ログ・エラー・トレースへ出さない。
- 地図は Leaflet + OpenStreetMap 標準タイルのみ、認証済みの小規模な対話利用に限る。帰属表示を出し、
  タイルの先読み・一括取得・オフラインキャッシュをしない。地図が私的な基点を露出してはならない。
- Leaflet 自体（JS・CSS・マーカー画像）と flatpickr（4.6.13、MIT）は `static/` 配下に vendoring し
  同一オリジンで配る（`adr/0010` と同じ規約）。認証済み画面は third-party script を1本も読まない。
- 候補検索の endpoint は認証済みの幹事に依存する（`adr/0006`）。参加者は署名付き共有リンク
  （ログインなし・名前自己申告・使い捨てトークン）で入る（`adr/0034`）。
- 認証済み候補画面のコントロールは、TDR-AUTH の素の HTTP DSL が観測する範囲では、クライアント JS が
  差し込むのではなく**サーバがレンダリングした HTML に出ていなければならない**

- **provider データが裏づけないことを主張しない。**居酒屋・バー系ジャンルの除外は「昼にやっている

  現金のみとは決して言わない。
- 会は店の情報を持たない。**保存するのは店 ID だけで、表示のたびに provider から取り直す**
  （`adr/0034` 決定6、live projection）。
- ブラウザに持たせた provider 由来の値には 24時間以下の上限を必ず付ける（provider 規約。下記）。

`manage.py` は `projects/dining-radar/.env.local` があれば読む（stdlib のみ・`os.environ.setdefault`
なので実プロセスの環境が必ず勝ち、ファイルが無ければ何もしない）。これは開発者の便宜専用で、
デプロイは `wsgi.py` を通り、このパスに一切依存しない。

## デプロイ先の規約と実測（2026-08-12 確認、2026-08-14 訂正）

- **Render 無料 web**: health check は**エッジを通さずサービスのポートへ直接届く**ので
  `X-Forwarded-Proto` を持たない。`Host` はサービスの `onrender.com` サブドメイン（または検証済み
  カスタムドメイン）。**5秒以内の 2xx か 3xx** で成功扱い。15分無通信でスピンダウンし、起床に約1分。
  月 750 インスタンス時間。ファイルシステムは揮発、SSH 無し。
- **Neon 無料**: プロジェクトあたり 100 CU時間・0.5GB、5分で scale-to-zero、10ブランチ、
  6時間の instant-restore。無期限（試用ではない）。Render 自前の無料 Postgres は作成30日で失効する
  ため採らなかった。
- **Hot Pepper**: 必須のテキスト表記は
  `Powered by <a href="http://webservice.recruit.co.jp/">ホットペッパーグルメ Webサービス</a>` で、
  API を使う全ページに出す。`serializers.PROVIDER_CREDIT` がこの文字列と完全一致し、`candidate.js`
  が描くので満たしている。飲食店から金を取るサイトでの利用は禁止（アフィリエイト収益は可）。
- **キャッシュ条項は存在する。**利用規約に
  `個別に定める規定がない場合はキャッシュの更新頻度を24時間以内と定めます` がある。取得情報を
  第三者のデータベースへ複製することも禁じている（このオリジンの `sessionStorage` はそれに当たらない）。

  > 2026-08-12 の記載は「provider はキャッシュ規則を定めていない」と書いていた。**これは誤り**で、
  > API リファレンスとご利用案内だけを読み、利用規約本体（`regulation.html`）も、**この件について
  > このプロジェクト自身が持っていた `adr/0018`（24時間という数字を 2026-08-09 から逐語で引用して
  > いた）も読まずに**否定を記録していた。教訓は「もっと web を読め」ではない。**外部規則が存在
  > しないと断言する前に、リポジトリ自身のその規則の記録を先に読め。**

**本番設定モジュールに対するローカル実測**（`RENDER` あり・`DJANGO_DEBUG` なし・Neon の代わりに
使い捨て SQLite）: `collectstatic` は 136 ファイルをコピーし 398 を後処理、manifest の欠落なし。
`X-Forwarded-Proto` 経由で `request.is_secure()` が真。ブラウザ相当の `Origin`/`Referer` を付けた
CSRF 有効なログイン POST が 302 を返すので、**Render のプロキシ配下では `CSRF_TRUSTED_ORIGINS` の
登録は要らない**。`sessionid` は Secure+HttpOnly+SameSite=Lax、`csrftoken` は Secure+SameSite=Lax。
`check --deploy` は `security.W005`・`W021`（HSTS の subdomains と preload、意図的に off）を出す。

本番ビルドはこれに加えて **`security.W009`** を出す。ローカルの検査では予測できなかった——検査側が
50文字の秘密を自前で与えていたのに対し、Render の `generateValue: true` は 256bit 乱数を base64 で
**44文字**にして渡すため、Django の `len < 50` の腕だけが引っかかる。長さヒューリスティックが密度を
読み違えているだけであり、これを回避しようとすると人間が署名鍵を見て貼る経路ができて却って悪い。
**そのままにしてある。**

**この方法で見つけて直した実害の欠陥**: `RENDER` あり・`X-Forwarded-Proto` なしの `GET /healthz` が
**301** を返していた（`SECURE_SSL_REDIRECT` が on で `SECURE_REDIRECT_EXEMPT` が空だった）。
Render はポートへ直接投げ 3xx を成功と見なすので、**readiness probe は `SELECT 1` を一度も走らせない
まま健康と報告されていた**。`SECURE_REDIRECT_EXEMPT = [r"^healthz$"]` を入れた。再実測: 素の HTTP の
`/healthz` は 200 `ok`、`/`・ログインパス・`/healthz/`・`/healthzz`・`/x/healthz` はすべて 301
——**完全一致のみで、前方一致でも部分一致でもない。**

## 公開オリジンの L5（2026-08-14、外部から curl で実測）

- `/healthz` は 200 `ok`。スピンダウン明けの初回は 15.2s（Render の公称の起床時間と一致）。
- `http://…/` は 301 で HTTPS へ。未認証の `/` は `/accounts/login/?next=/` へ 302。
- ログインページは 200 で、**`href` が1つも無い**——公開サインアップもメール再設定の導線も無い
  （`TDR-AUTH-03` の要求）。
- 実レスポンスのセキュリティヘッダ: `strict-transport-security: max-age=31536000`
  （includeSubDomains なし・preload なし、設計どおり）、`x-content-type-options: nosniff`、
  `x-frame-options: DENY`、`referrer-policy: strict-origin-when-cross-origin`、
  `cross-origin-opener-policy: same-origin`。
- 配信 HTML にもヘッダにも、API キー・座標・provider URL・範囲は出ていない。404 は 179バイトで
  フレームワーク名もトレースバックも設定も名指ししない。
- 認証済み画面は人間が確認（orchestrator は資格情報を持たない）: カードと地図が出る。必須の表記
  2件（`Powered by ホットペッパーグルメ Webサービス` と `© OpenStreetMap contributors`）とも出る。
  外部通信は OSM のタイル取得のみ——これは意図した境界である（`adr/0010` が Leaflet 自体を同一
  オリジンに vendoring し、タイルだけは必然的に OSM から取る。`product-brief.md` §3 が地図の表示
  範囲が provider に届くことを既に受け入れている）。`Referrer-Policy` がその開示をオリジンだけに
  抑える。**タイル URL の `z/x/y` は位置の開示そのものなので、issue・PR・コミットメッセージに
  貼らないこと。**
- **`/healthz` の除外は本番で効いていることを、推測ではなく実測した。**gunicorn のアクセスログを
  一時的に有効にすると `"GET /healthz HTTP/1.1" 200 2` が RFC1918 の私的アドレスから user agent
  `Render/1.0` で数秒おきに届いていた。200 は `SECURE_SSL_REDIRECT` を否定し、2バイトの body は
  `ok` なので view 自身が `SELECT 1` を走らせて答えており、私的な送信元はエッジを迂回していること
  の一次証拠になる。

  > ここへ至る過程で**検証手順自身の欠陥**が出た。2026-08-12 に `DEPLOYMENT.md` へ書いた
  > 「素の HTTP の `/healthz` が 200 を返すこと」は**公開インターネットからは実行不能**である
  > （Render のエッジが gunicorn より手前で 301 を返す）。代わりに Neon の compute を見る案を出したが、
  > 人間が試して「何も決まらない」と言った。**人間が正しい**——グラフの時間分解能が粗く、利用者の
  > トラフィック・検証のトラフィック・health check が同じ線に乗るので、5分と15分の閾値を区別できない。
  > `DEPLOYMENT.md` §3-3 はアクセスログ方式を規定し、Neon 方式を明示的に禁じている。**何も検証して
  > いないのに緑に見える検査は、検査が無いより悪い**——これは検証手順そのものにも当てはまる。
