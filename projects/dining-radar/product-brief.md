# Product Brief — ランチ候補をコンセプトから選び直せるレーダー

> **承認者向けサマリ**: 月1回程度の少人数ランチ会の幹事が、非公開の検索地点の周辺で、ランチ営業ありの店を「近さ重視」「人数に余裕がありそう」「普段と違うジャンル」などのコンセプトから選び、地図とカードで比較するためのプロダクトである。候補を固定件数ずつ追加するのではなく、別コンセプトで再提案する。公開リポジトリには生活圏・APIキー・実店舗データを置かず、初期の取得元は Hot Pepper グルメ Webサービス API のみとする。

> **状態**: 人間承認済み（2026-07-31、チャットでの「承認します」）。この承認はプロダクト意図を確定するものであり、後続の契約・ADR・設計・実装の承認を意味しない。

## 1. 目的と利用者

月1回程度のランチ会で、持ち回りの幹事が少人数の店選びを短時間で進められるようにする。利用者は、幹事として候補を比較し、店の外部情報で最終確認・予約をする人である。

最初の対象は、おおむね5人でのランチ会である。ただし、総席数は参考情報であり、希望人数の席・予約を保証するものではない。

## 2. 中心となる体験

1. 幹事が候補探索を開始する。検索基点はサーバーの非公開設定にある1地点で、ブラウザから入力も表示もしない。
2. アプリはランチ営業ありの候補集合を分析し、異なる観点のコンセプトをおおむね3つ示す。
3. 幹事がコンセプトを一つ選ぶと、その意図に合う店舗を地図とカードで比較する。
4. 気に入らなければ、候補を単に追加表示するのではなく、別コンセプトを選ぶ、または再提案を依頼して候補集合を入れ替える。
5. 幹事は各店舗の外部ページでメニュー、営業状況、予約可否などを最終確認する。

初期のコンセプト生成と順位付けは、説明可能な決定的ルールで行う。生成AIへ店舗情報を渡して選ばせることは初期スコープに含めない。

### コンセプトの例

- 近さを優先する
- グループ利用に余裕がありそうな店を優先する
- いつもと違うジャンルを試す
- 個室・禁煙など、APIで取得できる条件を重視する

コンセプト名、根拠、候補の並びは、取得できる情報だけで説明できなければならない。席の空き、予約可能性、支払方法など、APIが保証しない事実を推測・断定しない。

## 3. 表示する情報と操作

### 店舗カード

各候補には、比較と外部確認に必要な次の情報を表示する。

- 店名
- どんな店かが分かるジャンルと紹介文
- 営業時間と定休日
- 総席数（取得できない場合は「情報なし」）
- アクセス情報
- Hot Pepper の店舗ページへのリンク（メニュー等の確認先）
- 指定どおりの provider credit

ランチ営業の有無は候補条件として必須にする。開始時点では、特定日・曜日を入力して定休日や営業時間を自動判定する機能は持たない。価格帯は Hot Pepper の情報がディナー寄りであるため表示しない。現金のみ・PayPay可否などの支払方法も、信頼できる取得項目がないため表示・絞り込みしない。

### 地図

地図には Leaflet と OpenStreetMap の標準タイルを用いる。

- 候補店舗のマーカーとカードを相互に強調表示する。
- 表示範囲は返却された店舗マーカーから自動調整する。
- 検索基点、検索基点マーカー、徒歩経路、現在地、徒歩時間は表示しない。
- ブラウザへ渡す位置情報は候補店舗の位置だけとし、非公開の検索基点は送らない。
- OpenStreetMap の帰属表示を常に示す。タイルの事前取得・大量取得・オフラインキャッシュはしない。
- タイル提供者を将来差し替えられる境界を保つ。

通常の小規模な認証済み対話利用でも、地図タイルの取得先には閲覧された地図範囲が伝わる。この外部通信を受容できることを前提とし、位置の過度な精密表示は避ける。

### 補助的な絞り込み

コンセプト選択を候補の主操作とする。必要に応じて、検索範囲とジャンルは補助的な絞り込みとして扱う。手動ソートを主操作にはしない。具体的な値・API形状・状態遷移は、ブリーフ承認後の契約で定める。

## 4. 外部データと公開リポジトリの境界

初期の店舗情報源は Hot Pepper グルメ Webサービス API のみとし、スクレイピングと代替 provider は採用しない。

- APIキーはサーバーから provider へだけ送る。キー入りURLをブラウザ、ログ、エラー、トレース、Gitに出さない。
- 実在の検索地点、地名、座標、既定探索距離、生活圏が推測できる例を Git に置かない。
- 実店舗ID、実店舗のレスポンス・画像・fixture・dump・データ移行を Git に置かない。テストやデザインは合成データのみを使う。
- 初期版は provider レスポンスを cache・永続化しない。店舗事実を改変・再配布しない。
- 表示義務と利用規約は、実装前・公開運用前・cacheや永続化の導入前に公式文書で再確認する。

Hot Pepper の店舗ページへのリンクは、詳細情報と予約可否を利用者が確認するための導線である。アプリ自身が予約可否やメニュー内容を保証・複製するものではない。

## 5. 認証と公開範囲

ランチ会の幹事が持ち回りで使えるよう、将来はインターネットからアクセス可能にする。候補探索は認証済みの幹事だけが使える機能とする。

初期の想定は、管理者が招待した個別アカウントを使い、公開サインアップは設けない形である。ただし、アカウントの発行・無効化、ログイン・ログアウト、パスワード再設定、HTTPS、Cookie、CSRF、レート制限、デプロイ構成は別スライスで判断・契約する。今回のブリーフはそれらの実装方式を決めない。

## 6. 将来検討する項目

- 過去に行った店を避ける履歴、ブラックリストの登録・解除、利用結果に基づく推薦改善
- 長期照合に provider ID または HMAC を使う可否。これは provider 規約を確認するまで導入・公開運用しない。HMAC は識別子の匿名化や規約適合を保証しない。
- 開催日を入力した営業日判定
- 予約や人数の確実性を扱う連携
- 地図タイル提供者の変更

## 7. 初期スコープから除外するもの

- 「次の5件」「もっと見る」による固定ページングを中心体験にすること
- スクレイピング、複数 provider、provider画像の利用
- 実時間の空席・予約可否・支払方法・徒歩経路・現在地の提供
- 価格帯・ディナー予算の表示
- 公開サインアップ、認証・デプロイ機構の具体実装
- 生成AIによる候補選定

## 8. 未決事項と承認後の作業

### 未決事項

- コンセプトの最終的な種類・表示文言・選択条件
- 補助フィルタの具体的な値と、Hot Pepper API への対応
- 初回表示件数、再提案時の候補集合の扱い、エラー時の画面状態
- Leaflet/OSM のライセンス表記を含む具体的な画面設計
- 外部公開に必要な認証・運用設計

### 受け入れの目安

- 幹事が「近さ」「グループ利用の参考」「ジャンル変化」など、選ぶ理由の異なる提案から候補を比較できる。
- 候補を増やし続けるのではなく、再提案で探索の切り口を変えられる。
- 店舗カードと地図で、場所、定休日、営業時間、店の種類、席数の参考、外部詳細への導線を確認できる。
- 非公開の検索地点、秘密、実店舗データを公開リポジトリへ持ち込まない。

### このブリーフ承認後の順序

1. 候補探索の受け入れ契約・API契約・必要なADRを、このブリーフに沿って改訂する。
2. 契約に整合するデザインブリーフとレビュー用プレビューを作り直す。
3. 認証・公開運用を別スライスとして契約する。
4. それぞれの人間承認後に実装スライスへ進む。
