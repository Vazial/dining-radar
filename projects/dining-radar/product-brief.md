# Product Brief — ランチ候補をコンセプトから選び直せるレーダー

> **承認者向けサマリ**: 月1回程度の少人数ランチ会の幹事が、非公開の検索地点の周辺で、ランチ営業ありの店を「近さ重視」「人数に余裕がありそう」「普段と違うジャンル」などのコンセプトから選び、地図とカードで比較するためのプロダクトである。候補を固定件数ずつ追加するのではなく、別コンセプトで再提案する。公開リポジトリには生活圏・APIキー・実店舗データを置かず、初期の取得元は Hot Pepper グルメ Webサービス API のみとする。

> **状態**: 人間承認済み（2026-07-31、チャットでの「承認します」）。この承認はプロダクト意図を確定するものであり、後続の契約・ADR・設計・実装の承認を意味しない。**§3・§7の予算感（ディナー予算の目安表示）に関する記述は2026-08-09にADR-0019決定8として改訂されたものであり、この改訂は人間の再承認点である。承認の実体は本PRのマージである。**

## 1. 目的と利用者

月1回程度のランチ会で、持ち回りの幹事が少人数の店選びを短時間で進められるようにする。利用者は、幹事として候補を比較し、店の外部情報で最終確認・予約をする人である。

最初の対象は、おおむね5人でのランチ会である。ただし、総席数は参考情報であり、希望人数の席・予約を保証するものではない。

## 2. 中心となる体験

1. 幹事が候補探索を開始する。検索基点はサーバーの非公開設定にある1地点で、ブラウザから入力も表示もしない。
2. アプリはランチ営業ありの候補集合を分析し、異なる観点のコンセプトをおおむね3つ示す。
3. 幹事がコンセプトを一つ選ぶと、その意図に合う店舗を地図とカードで比較する。
4. 気に入らなければ、候補を単に追加表示するのではなく、別コンセプトを選ぶ、または再提案を依頼して候補集合を入れ替える。
5. 幹事は各店舗の外部ページでメニュー、営業状況、予約可否などを最終確認する。

初期のコンセプト生成と順位付けは、説明可能な決定的ルールで行う。生成AIへ店舗情報を渡して選ばせることは初期スコープに含めない。

### コンセプトの例

- 近さを優先する
- 候補の中で最も件数の多いジャンルへ絞り込んで比較する（ADR-0019。「いつもと違うジャンルを試す」という当初の切り口は縮退のため廃止し（後述）、代わりに実データで良好な分布が確認できたジャンルの多さそのものを絞り込みの基準にする切り口へ組み替えた）
- 禁煙対応（全面禁煙・一部禁煙・禁煙席なし）を参考に比較する（ADR-0019。個室・駐車場等を合算する当初の切り口は、構成フィールドの大半が実データで使えないと判明したため廃止し、実データで良好だった禁煙区分単独の切り口に置き換えた）
- 居酒屋・バーなど、ランチ営業が確認しづらいジャンルも含めて探す（ADR-0015。既定の候補・他のコンセプトからは除き、この切り口を選んだときだけ含める）

総席数（多い順に並べる切り口）と予算感（安い順に並べる切り口）は、いずれも「並べ替えの基準としての価値がない」と人間自身が判断したため、コンセプトからは外した。代わりに、すべての店舗カードへ常時表示する目安（総席数は少なめ／標準／多め、予算感はディナー目安の3段階）として使う（後述、店舗カード節）。

コンセプト名、根拠、候補の並びは、取得できる情報だけで説明できなければならない。席の空き、予約可能性、支払方法など、APIが保証しない事実を推測・断定しない。

「いつもと違うジャンルを試す」という切り口は、2度目の実データレビューで、近さ優先の初期切り口と常に同じ候補・同じ順序に縮退することが判明したため廃止した（ADR-0016）。代わりに、現在表示中の切り口のまま新しい提案を依頼するだけの「もう一度探す」という操作を追加した。これは独自の選ぶ理由を持つコンセプト（切り口）ではなく、既表示候補の二次的な順位低下だけに頼る別の操作である。3度目の実データレビューでは、この順位低下が表示上限5件（ADR-0015）と組み合わさって機能しなくなっていたことが判明し、実施箇所をブラウザからサーバへ移した（ADR-0017）。実データのフィールド調査（ADR-0019）を受け、ジャンルは「候補の中で最も件数の多いジャンルへ絞り込む」という別の組み方で切り口として復活させた——この組み方は、絞り込んだ候補集合が常に近さ優先の候補集合の真部分集合になるよう設計されており、以前の切り口が犯した「完全に同じ候補・順序になる」という縮退を構造的に再発させない。

## 3. 表示する情報と操作

### 店舗カード

各候補には、比較と外部確認に必要な次の情報を表示する。

- 店名
- どんな店かが分かるジャンルと紹介文
- 定休日
- 総席数の目安（少なめ／標準／多め。取得できない場合は「情報なし」。ADR-0019——正確な数値でのソートに価値がないという実データレビューでの判断により、比較の切り口からは外し、常時表示する参考の目安に変えた）
- 禁煙対応の目安（全面禁煙／一部禁煙／禁煙席なし。取得できない場合は「情報なし」。ADR-0019）
- 予算感の目安（ディナー目安として3段階のいずれか。取得できない場合は「情報なし」。必ず「ディナー」であることが分かる表現で示し、ランチの価格は推測・断定しない。ADR-0019決定8）
- クレジットカードが利用できない店舗には、その旨の注意（「クレジットカードは利用できません。お支払い方法は店舗にご確認ください」）。利用できる、または情報がない場合は何も表示しない。「現金のみ」とは断定しない——取得できるのはクレジットカードの可否だけであり、他の決済手段の可否は分からないため（ADR-0019）
- Hot Pepper の店舗ページへのリンク（メニュー等の確認先）
- 指定どおりの provider credit

アクセス情報は、地図が同じ位置情報を示すため、実データレビューでの指摘を受けてカードから外した（ADR-0019）。営業時間は、3度目の実機レビューでモバイル画面の1フィールドとして最も縦に長く（実測: カード全体345pxのうち55px）、見づらいとの指摘を受けてカードとAPI応答の両方から外した（ADR-0017）。この削除は「時間帯で確認済みだから表示が不要になった」という意味ではない——Hot Pepperの`lunch`応答値は「あり」のみでランチ提供の実態を示さず、`open`は自由記述で機械判定できないため、この製品は今も店舗ごとの正確な営業時間帯を確認できていない。営業時間は引き続きHot Pepper店舗ページで確認する。

ランチ営業の有無は候補条件として必須にする。開始時点では、特定日・曜日を入力して定休日や営業時間を自動判定する機能は持たない。**価格帯（ディナー予算）の扱い（2026-08-09、ADR-0019決定8で改訂。人間の再承認点）**: Hot Pepperの`budget`情報はディナー寄りであり、ランチ価格帯そのものは表示・推測しない。ただし実データのフィールド調査で価格帯情報自体は充足率100%で取得できることが確認できたため、「ディナー予算であることを明示したうえでの粗い3段階の目安」として、上記の店舗カード節のとおり表示する。ランチ価格の推論・断定（例: 「ランチはおおむね1000円以下」といった主張）はいかなる形でも行わない。この判断は、当初のドラフトで全面却下されていたものが、その却下理由の一部（本ブリーフの旧来の除外記述の一部を根拠として引用していた点）が循環していたことが判明し、人間が「ざっくりの段階表示ができるなら入れてほしい」と再確認したことで差し戻された経緯を持つ。

居酒屋・バーなど、Hot Pepper の取得可能フィールドだけではランチ営業の実施を確認できないジャンルは、既定の候補と他のコンセプトからは除く。これは「ランチをやっていない」という確定した判断ではなく、確認できないという理由による。含めて比較したい場合は、専用のコンセプト（上記）を選ぶ（ADR-0015）。

各コンセプトで比較用に表示する候補は最大5件とする。順位付け自体は取得・正規化した候補全体に対して行い、5件は表示段階だけの上限である（ADR-0015）。

### 地図

地図には Leaflet と OpenStreetMap の標準タイルを用いる。

- 候補店舗のマーカーとカードを相互に強調表示する。
- 表示範囲は返却された店舗マーカーから自動調整する。
- 検索基点、検索基点マーカー、徒歩経路、現在地、徒歩時間は表示しない。
- ブラウザへ渡す位置情報は候補店舗の位置だけとし、非公開の検索基点は送らない。
- OpenStreetMap の帰属表示を常に示す。タイルの事前取得・大量取得・オフラインキャッシュはしない。
- タイル提供者を将来差し替えられる境界を保つ。

通常の小規模な認証済み対話利用でも、地図タイルの取得先には閲覧された地図範囲が伝わる。この外部通信を受容できることを前提とし、位置の過度な精密表示は避ける。

### 補助的な絞り込み

コンセプト選択を候補の主操作とする。必要に応じて、検索範囲とジャンルは補助的な絞り込みとして扱う。手動ソートを主操作にはしない。具体的な値・API形状・状態遷移は、ブリーフ承認後の契約で定める。

## 4. 外部データと公開リポジトリの境界

初期の店舗情報源は Hot Pepper グルメ Webサービス API のみとし、スクレイピングと代替 provider は採用しない。

- APIキーはサーバーから provider へだけ送る。キー入りURLをブラウザ、ログ、エラー、トレース、Gitに出さない。
- 実在の検索地点、地名、座標、既定探索距離、生活圏が推測できる例を Git に置かない。
- 実店舗ID、実店舗のレスポンス・画像・fixture・dump・データ移行を Git に置かない。テストやデザインは合成データのみを使う。
- 初期版は provider レスポンスを cache・永続化しない。店舗事実を改変・再配布しない。
- 表示義務と利用規約は、実装前・公開運用前・cacheや永続化の導入前に公式文書で再確認する。

Hot Pepper の店舗ページへのリンクは、詳細情報と予約可否を利用者が確認するための導線である。アプリ自身が予約可否やメニュー内容を保証・複製するものではない。

## 5. 認証と公開範囲

ランチ会の幹事が持ち回りで使えるよう、将来はインターネットからアクセス可能にする。候補探索は認証済みの幹事だけが使える機能とする。

初期の想定は、管理者が招待した個別アカウントを使い、公開サインアップは設けない形である。ただし、アカウントの発行・無効化、ログイン・ログアウト、パスワード再設定、HTTPS、Cookie、CSRF、レート制限、デプロイ構成は別スライスで判断・契約する。今回のブリーフはそれらの実装方式を決めない。

## 6. 将来検討する項目

- 開催日を入力した営業日判定
- 予約や人数の確実性を扱う連携
- 地図タイル提供者の変更

## 7. 初期スコープから除外するもの

- 過去に行った店を避ける履歴、ブラックリストの登録・解除、利用結果に基づく推薦改善。これは初期版だけの見送りではなく、現在の製品方針として採用しない。再検討には新たな人の意思決定とADRを必要とする。同じ画面内で直前に表示した候補を再提案時に後回しにする仕組み（ADR-0008、ADR-0017）は、この方針の対象外である——サーバへ送る一覧はサーバ自身が直前に返した値の単純な echo であり、保存されず、次の1回の再提案にしか使われないため、ここでいう履歴には当たらない。
- 長期照合のための provider ID または HMAC の保存・利用。これも現在の製品方針として採用しない。再検討には新たな人の意思決定、provider規約の再確認、ADRを必要とする。

> この方針更新と ADR-0008 は 2026-08-03 の chat で人が承認した。現在の candidate-search PR がマージされた時点で durable decision となる。

- 「次の5件」「もっと見る」による固定ページングを中心体験にすること
- スクレイピング、複数 provider、provider画像の利用
- 実時間の空席・予約可否・徒歩経路・現在地の提供
- ディナー予算からランチ価格帯を推測・断定すること（ADR-0015が確立した「確認できないことを断定しない」原則をそのまま適用する）。**ディナー予算をディナー予算と明示したうえでの粗い段階表示（`dinnerBudgetTier`）はこの除外の対象外であり、上記「店舗カード」節のとおり表示する**（2026-08-09、ADR-0019決定8。人間の再承認点。承認の実体は本PRのマージである。当初のドラフトはこの段階表示も含めて全面除外としたが、その根拠の一部が循環していたことが判明し、人間の再確認で差し戻された）
- クレジットカード以外の支払方法（現金のみの断定、PayPay等の個別キャッシュレス手段の可否）の表示・絞り込み。クレジットカードの利用可否だけは、信頼できる単一の取得項目として例外的にカードの注意表示にだけ使う（ADR-0019。上記「店舗カード」節参照）
- 公開サインアップ、認証・デプロイ機構の具体実装
- 生成AIによる候補選定

## 8. 未決事項と承認後の作業

### 未決事項

- コンセプトの最終的な種類・表示文言・選択条件（居酒屋・バー等ランチ営業が確認しづらいジャンルを含める切り口はADR-0015で追加した。ジャンルを横断して比較する切り口は実データで縮退が判明したためADR-0016で廃止し、同ADRで「もう一度探す」という別操作を追加した。実データのフィールド調査を受け、ADR-0019は総席数・個室等を合算する切り口を廃止し、最多ジャンルへ絞り込む切り口と禁煙区分の切り口を新設した。現在の切り口は「近さ」「最多ジャンルへの絞り込み」「禁煙対応」「居酒屋・バーを含める」の4種類である。他の種類・文言は今後も必要に応じて見直す）
- 補助フィルタの具体的な値と、Hot Pepper API への対応
- ~~初回表示件数~~、再提案時の候補集合の扱い、エラー時の画面状態（初回表示件数はADR-0015で最大5件と決定した。再提案時の候補集合の扱い・エラー時の画面状態は引き続き未決）
- Leaflet/OSM のライセンス表記を含む具体的な画面設計
- 外部公開に必要な認証・運用設計
- `capacityTier`（総席数の目安）・`dinnerBudgetTier`（予算感の目安）のしきい値は、いずれも一回限りの実データ診断に基づく暫定値であり、より多くの実データが得られた時点で見直しの要否を確認する（ADR-0019）

### 受け入れの目安

- 幹事が「近さ」「ジャンルの絞り込み」「禁煙対応」など、選ぶ理由の異なる提案から候補を比較できる。
- 候補を増やし続けるのではなく、再提案で探索の切り口を変えられる。
- 店舗カードと地図で、場所、定休日、店の種類、席数の目安、禁煙対応の目安、予算感の目安、外部詳細への導線を確認できる。営業時間はHot Pepper店舗ページへのリンクから確認する（ADR-0017）。
- 非公開の検索地点、秘密、実店舗データを公開リポジトリへ持ち込まない。

### このブリーフ承認後の順序

1. 候補探索の受け入れ契約・API契約・必要なADRを、このブリーフに沿って改訂する。
2. 契約に整合するデザインブリーフとレビュー用プレビューを作り直す。
3. 認証・公開運用を別スライスとして契約する。
4. それぞれの人間承認後に実装スライスへ進む。
