# ADR-0067: WebをECS Fargate単一タスク（ALB無し、Caddyサイドカー＋Elastic IP自動付け替え）へ移行する

> **承認者向けサマリ**: KEN-27〜29の比較検討（本ADR旧版が記録していた「決定を下さない」比較材料）を
> 踏まえ、2026-09-28のチャットで人間が最終決定を下した。Web（現行Render）を**ECS Fargate単一タスク
> （0.25vCPU/0.5GB程度）へ移行し、ALBは使わない**。DB（現行Neon）は変更しない。タスク内にCaddyを
> サイドカーとして同居させてTLS終端し、パブリックサブネットのタスクENIへElastic IPを直接アタッチ、
> 再デプロイのたびに変わるENI/IPへは小さなLambda（EventBridge起動）が自動で付け替える。ログは
> CloudWatch Logs、アラーム・ダッシュボードもCloudWatch、secretはSSM Parameter Store、イメージは
> ECR、DNSは既存のRoute 53ホストゾーンを流用する。**概算合計は月$4〜5**——Fargateタスク本体がほぼ
> 唯一の実質コストで、他は常時無料枠に収まる規模と見積もっている。学習目的（ECSそのものを学びたい）
> を最優先し、運用が最も楽なApp Runner案（旧版が検討していた本命候補）と、ECSの王道であるALB付き
> 構成の両方を、比較のうえ不採用とした。ALB不採用の代償（WAFが使えない、再デプロイ時に数十秒〜1分の
> 接続断）は人間が確認済みで許容している。**本ADR記載の料金はAWS公式ページのWebFetch概算であり、
> 正式なAWS Pricing Calculator見積りではない**——実装（KEN-31）着手前に裏を取ることを帰結に明記する。

## 文脈

KEN-27は、`adr/0021`が採用した現行構成（無料Render Web + 無料Neon Postgres）に伴う無料枠固有の
制約を洗い出すところから始まった。動機は、`adr/0021`帰結が「NeonまたはRenderの無料条件が変わった
場合は、費用発生前に停止し、paid化または移転を再判断する」という条件付きのセーフティネットを
定めているのに対し、実際にその条件変化へどれだけ近づいているかを確かめる材料がこれまで整理されて
いなかったことにある。

KEN-28は確定した制約8項目（Render側5項目・Neon側3項目）を`activeContext.md`の実測・`adr/0021`の
記述と突き合わせ、**Neonの5分scale-to-zeroだけは「困っているかどうかを確かめる手段自体が無い」
（しかもその手段は一度試みて失敗し`DEPLOYMENT.md` §3-3が明示的に禁じている）**という、他の
「要実測」項目とは性質の異なる所見を報告した。KEN-29はこれを比較軸に、AWS移行の3選択肢（全置換／
DBのみ置換／現状維持）を、料金・上限の断定を避けて比較し、本ADRの旧版は**決定を下さず**3選択肢を
比較材料として並べるだけに留めていた（`status: 提案中`）。

2026-09-28のチャットで、人間がこの比較を踏まえて次のラウンドの検討に進み、最終決定に至った。
やり取りの経緯: (1) まず移行の動機を確認し、(2) AWS移行の置換範囲は比較したうえで決めたいという
回答を得て、(3) 人間から「ECS Fargateを軸に検討したい」という希望（学習目的——ECSそのものを
使えるようになりたい）が示された。(4) ECS Fargate案と、運用が最も楽で当初推奨だったApp Runner案の
コスト比較を提示したところ、(5) 人間から「ECSのほうがいいかも」という応答があり、(6) ALB無し構成
（コスト最優先）へ検討を寄せた。(7) CloudWatch・Route 53・ECR・SSM Parameter Store等を全部載せても
コスト概算が変わらないことを確認し、(8) ALB無しのデメリット（再デプロイ時の接続断、AWS WAFが
使えないこと）を提示、(9) セキュリティへの影響（このアプリの招待制という性質との整合）を確認した
うえで、(10) 人間が「よさそう！」と最終承認した。

## 検討した代替案

実際にこのチャットで検討され、却下された4案を理由つきで記録する。

### 1. AWS App Runner

運用が最も楽で、コストもECS Fargate単一タスク案と同程度（月$3〜10）。チャットの初期段階ではこれを
推奨していた。しかし人間がECSそのものを学びたいという学習目的を持っており、App Runnerはコンテナ
オーケストレーションの詳細（タスク定義、ネットワーキング、サイドカー構成等）を隠蔽してしまうため、
学習目的を優先して不採用とした。

### 2. ECS Fargate + ALB

ECSの王道パターン（ターゲットグループ連携）を学べる構成。しかしALBの固定費が月$22〜23かかり、
合計で月$25〜30と3選択肢の中で最も高くなる。学習効果はある（ALB連携もECSの一部）が、コストを
最優先したため不採用とした。

### 3. ECS Fargate + EC2セルフホストproxy + Cloud Map（ALB代わりにEC2でリバースプロキシを自作）

ALBの代わりにEC2インスタンス1台でリバースプロキシを自作し、Cloud Mapでサービスディスカバリする
構成。月$8〜10と見積もった。しかしEC2という別個の管理対象（OSパッチ、セキュリティグループ、
インスタンスの死活監視）を新たに抱えることになり、Caddyサイドカー方式（タスク内に同居させるだけ）
の方が管理対象を増やさずに同等以上にシンプルかつ安価であるため不採用とした。

### 4. EC2 1台 + Docker + Caddy（ECSを使わない）

最も枯れていて壊れにくい構成。EC2インスタンスは基本的に再起動しない限りElastic IPが変わらないため、
本採用案が必要とする「IP自動付け替えの仕組み」自体が不要になる。月額はFargate単体案とほぼ同額
（$4〜5）。しかし人間の学習対象が「ECSそのもの」であるため、ECSを使わないこの案は希望に反すると
判断して不採用とした。**リスクを避けたくなった場合の代替案として、本ADRに記録しておく。**

## 決定

Web（現行Render）を、**ECS Fargate単一タスク（0.25vCPU/0.5GB程度）へ移行し、ALBは使わない**。
DB（現行Neon）は変更せず現状維持する。

具体的構成は次のとおりである。

1. **Caddyサイドカー**: タスク内にCaddyコンテナをサイドカーとして同居させ、Let's EncryptでTLS
   終端する。アプリコンテナへはタスク内localhost経由でプロキシする。
2. **配置とElastic IP**: パブリックサブネットに配置し、Elastic IPをタスクのENIへ直接アタッチする。
3. **IP自動付け替え**: タスクは再デプロイのたびに新しいENI/IPになるため、ECSタスク状態変化
   イベント（EventBridge）をトリガーに、小さなLambdaがElastic IPを新タスクへ再アタッチする。
4. **ログ**: CloudWatch Logs（awslogsドライバ）。常時無料枠5GB/月に収まる想定。
5. **監視**: CloudWatchアラーム（10個まで常時無料）・ダッシュボード（3個まで常時無料）を使う。
6. **DNS**: Route 53は既存のホストゾーンをそのまま使う（新規費用なし）。
7. **イメージ保存**: ECRを使う。このAWSアカウントは1年以上使用済みのため新規顧客無料枠
   （500MB/月・1年間）の対象外だが、数百MB程度で$0.10/GB、実質数セントに収まる見積り。
8. **secret管理**: SECRET_KEY・Neon接続文字列等はAWS Secrets ManagerではなくSSM Parameter
   Store（Standard・SecureString、AWS管理鍵）を使う。Secrets Managerは$0.40/secret/月かかるが、
   SSM Parameter Store Standardは無料であるため。

**コスト概算合計は約$4〜5/月**で、Fargateタスク本体がほぼ唯一の実質コストであり、他は全て常時
無料枠内に収まる規模と見積もっている。

この構成を選ぶ理由は、人間の学習目的（ECSそのものを学びたい）とコスト最優先の両方を同時に満たす
点にある。ALB付きの王道構成（代替案2）はコストが最大になるため退け、App Runner（代替案1）は
学習目的を満たさないため退け、EC2セルフホストproxy（代替案3）はCaddyサイドカーで同等の効果を
より単純に得られるため退けた。

## 帰結

### セキュリティ上のトレードオフ

- ALBを使わないと、AWS WAF（マネージドのSQLi/XSS/bot対策ルール）が使えない。これが本決定における
  唯一の実質的なセキュリティ機能差である。
- AWS Shield Standard（L3/L4 DDoS対策）が、Elastic IP単体に対してALBと同等に効くかは、AWS公式
  ページ（shield/features/）で明言されておらず**要検証のまま残す**。
- このアプリは招待制アカウント・署名付き使い捨てリンクで運用され、公開フォーム・サインアップ導線を
  持たない。Djangoの標準防御（CSRF、ORM由来のSQLi対策、secure cookie）は既に`adr/0021`で導入
  済みである。招待制の身内向けツールという前提のもとでは、WAF不在は許容範囲と人間が判断した。
  **現状のRenderもWAF相当の機能を持たないため、この決定はセキュリティ面の後退ではなく現状維持
  である。**

### 運用上のトレードオフ

- ALB無し・単一タスクのため、再デプロイのたびに数十秒〜1分程度の接続断が起きる（ALBによる無停止
  ローリングデプロイが無い）。
- Elastic IP自動付け替えの仕組み（Lambda）自体が新しい壊れどころになり得る（IAM権限ミス、古い
  タスクがENIからIPを離す前に新タスクが取りに行くタイミングのズレ等）。デプロイは利用の無い時間帯に
  行う運用規律が必要であり、人間はこれを受け入れ済みである。
- 単一タスクのため冗長性が無い。この用途では許容と人間が判断した。

### 料金についての留保

本ADR記載の料金はすべて、AWS公式料金ページをWebFetch（自動要約ツール）で取得した概算であり、
AWS Pricing Calculatorでの正式な見積りではない。**実装（KEN-31）に入る前に、正式な見積りで裏を
取ること**を本帰結として明記する。

### 実装と実リソース作成の分担

新しい規程・契約はいずれも本ADRの対象外である。実装作業はKEN-31で行う。AWS側の実リソース作成
（Fargateサービス作成、Lambda/EventBridge設定、Route 53切替）は、`adr/0021`の前例（実リソース
作成とsecret投入は外部状態変更であり、コードのマージとは別に人間確認を要する）と同じ扱いとし、
**人間が行う必要がある**。
