# ADR-0067: Render+Neon無料枠からAWSへの移行を検討する

> **承認者向けサマリ**: `adr/0021`が定めた無料Render Web + 無料Neon Postgresの構成には、無料枠固有の
> 制約が8項目ある。KEN-28はこの8項目を`activeContext.md`の実測・`adr/0021`の記述と突き合わせ、
> ほとんどは「当面問題ない」または「要実測（実測すればいずれ埋まる空白）」だが、**Neonの
> 5分scale-to-zeroだけは「困っているかどうかを確かめる手段自体が無い」——しかもその手段は一度
> 試みて失敗し`DEPLOYMENT.md` §3-3が明示的に禁じている**、という性質の異なる所見を報告した。
> KEN-29はこれを比較軸に、AWS移行の3選択肢（全置換／DBのみ置換／現状維持）を、料金・上限の断定を
> 避けて比較した。**本ADRはこの比較を記録するのみで、決定は下さない**（status: 提案中のまま）。
> 3選択肢いずれも推奨として残し、人間が選ぶ必要がある論点7点を明記する。

## 文脈

KEN-27は、`adr/0021`が採用した現行構成——無料Render Web（Singapore、1 instance・Gunicorn 1
worker）と無料Neon Postgres（account・password hash・Django session・migration stateのみ保存）
——に伴う無料枠固有の制約を洗い出すところから始まった。動機は、`adr/0021`帰結が「NeonまたはRenderの
無料条件が変わった場合は、費用発生前に停止し、paid化または移転を再判断する」という条件付きの
セーフティネットを定めているのに対し、実際にその条件変化へどれだけ近づいているかを確かめる材料が
これまで整理されていなかったことにある。

KEN-28は、確定した制約8項目（Render側5項目・Neon側3項目）それぞれについて、`activeContext.md`
「デプロイ先の規約と実測」節・「公開オリジンのL5」節・「確定ポリシー」節、および`adr/0021`の記述を
突き合わせ、「今すでに困っている／まだ困っていないが近づいている（要実測）／当面問題ない」のいずれかに
判定した。新たな外部調査・本番アクセスは行っていない。結果は次のとおりである（数値は
`activeContext.md`が既に持つ実測・規約記述の引用であり、本ADRは新たな数値を主張しない）。

| # | 項目 | KEN-28の判定 |
|---|---|---|
| 1 | Render cold start 約1分 | 当面問題ない（規約値「約1分」とL5実測「15.2s」に開きがあり、この一点のみ数値の突き合わせが要確認） |
| 2 | Render 15分idle spin down | 当面問題ない（`adr/0021`が「5人程度の断続的な利用」を前提に明示的に許容した設計。前提利用規模自体の実測は無い） |
| 3 | Render 月750インスタンス時間上限 | 要実測（消費インスタンス時間の記録が両文書に無い） |
| 4 | Render 永続FS無し | 当面問題ない（設計自体が最初から非依存。live projection方針＝店データを保存しないこと、`adr/0034`決定6と整合） |
| 5 | Render SSH無し | 当面問題ない（`adr/0021`決定6が無い前提で運用設計済み。着手できなかった作業の記録は無い） |
| 6 | Neon 100 CU時間/月 | 要実測（CU時間消費の記録が両文書に無い） |
| 7 | Neon 0.5GB | 要実測（DB使用量の記録が両文書に無い。永続化対象を account・session・migration state に限定する設計判断自体は`adr/0021`決定2が既に記録済み） |
| 8 | Neon 5分 scale-to-zero | ユーザー影響は要実測。ただし**観測手段自体が無いことは今すでに困っている**——Neonのcompute活動グラフで5分/15分の閾値を区別する検証手順は一度試みられ、時間分解能が粗く区別できないと判明して失敗し、`DEPLOYMENT.md` §3-3が以後この方式の使用を明示的に禁じている |

最も重い所見は項目8である。「困っているかどうか」を機械的に確かめる手段そのものが無く、かつその手段は
一度試みて失敗し禁止済みという点で、他の「要実測」項目（3・6・7）——実測作業さえ行えばいずれ埋まる
空白——とは性質が異なる。項目1・2・4・5は、`adr/0021`が明示的に許容した設計判断を覆す動機が無い限り、
移行の是非そのものを左右しない。

`adr/0021`追記（2026-08-14）により、Route 53は既に本番DNSとして使用中であり、AWSアカウントとの
接点は既存である（証明書・IAM等の初期整備コストの一部は既に発生済みと見なせる）。

## 検討した代替案

KEN-29は、上記の判定（特に項目8の「今すでに困っている」を最優先の軸、項目3・6・7の「要実測」を
次点の軸）を比較材料に、AWS移行の3選択肢を比較した。**架空の料金・上限値は挙げず、一般に知られる
サービス特性の範囲でのみ記述し、正確な数字はすべて「要検証」「要見積り」と明記する**——この留保は
本ADRでもそのまま引き継ぐ。AWS側候補（App Runner／ECS Fargate／Lightsail Containers、
RDS for PostgreSQL／Aurora Serverless v2）の「無料枠」が、Neonの無期限無料枠と同じ性質・恒久性を
持つとは限らない点も、比較全体を通じた留保として引き継ぐ。

### 選択肢1: 全置換（Web・DBともAWSへ）

- **長所**: 項目3（Render 750h上限）・項目6・7（Neon CU時間・容量）を、AWS側の従量/固定課金モデルへの
  置換によって構造的に解消できる可能性が最も高い。項目8（scale-to-zero観測手段の欠如）も、DB側に
  常時起動のRDS for PostgreSQLを選べば、scale-to-zero自体が発生しなくなることで問題が消滅する。
  Route 53からの切替はDNS作業のみで完結する。
- **短所**: CI/CDパイプラインの全面新設（コンテナビルド・ECRプッシュ・デプロイ）、IAM・ネットワーク
  （VPC、セキュリティグループ等）の新規設計、監視・ログ基盤の新設が要る——3選択肢の中で移行コスト・
  運用負荷が最大。無料運用から固定費/従量費のある運用への転換になり、具体額は要見積り。静的配信を
  S3/CloudFront等の別オリジンへ切り出す設計にすると、Leaflet同一オリジンvendoring規約（`adr/0010`）に
  抵触するため、切り出す場合は同一ドメイン配下に収める追加設計が要る（アプリコンテナからの配信を
  維持する限りは抵触しない）。Aurora Serverless v2でpause/resume相当機能を使う設計にすると、
  項目8と同種の「粗い観測手段しかない」問題が再発し得る（要検証）。

### 選択肢2: DBのみ置換（NeonをAWS Postgresへ、RenderのWebは維持）

- **長所**: 変更範囲がDB接続情報とスキーマ移行に限定され、3選択肢の中で移行コスト・運用負荷が最小に
  近い。CI/CDはRenderの既存自動デプロイ（`autoDeployTrigger: checksPass`）をそのまま維持でき、
  変更は接続文字列等のruntime secret更新に留まる可能性が高い。項目6・7は解消し得る。項目8も、
  RDSを常時起動で選ぶ場合は問題自体が消滅する。項目1・2・4・5はWebを変更しないため現状のまま
  （`adr/0021`決定1・3・6の前提が維持される）。同じPostgresであるためスキーマ・データ移行自体は
  技術的には低リスク。
- **短所**: 項目3（Render 750h上限）は未解消のまま——Webを変えない以上この選択肢では動かない。
  RenderのWebアプリからAWS RDS/Auroraへのネットワーク到達経路（publicly accessibleにするか、
  Renderの送信元IPを許可リスト化できるか）が選択肢2固有の新しいリスク・検証項目として発生する
  （Renderの送信元IPが固定・公開されているか自体が要確認）。TLS必須（`adr/0021`決定2）を満たすため
  AWS側で明示的な設定作業が要る（方針抵触ではなく設定タスク）。DB分のみ新たな費用が発生し、
  正確な比較は要見積り。

### 選択肢3: 現状維持（Render+Neonのまま）

- **長所**: `adr/0021`自体が現状構成の根拠であるため比較の基準点として完全に適合し、ポリシー抵触
  リスクが無い。費用は無料枠のまま変化せず、移行負荷は定義上ゼロ。
- **短所**: 項目3・6・7は要実測のまま残る（ただしこの実測作業自体はどの選択肢を取っても別途必要に
  なり得る、現状維持特有ではない作業である）。項目8（観測手段の欠如）が未解消のまま残る——これが
  KEN-28で「今すでに困っている」と判定された唯一の項目であるため、現状維持を取るならこの点への
  対応案を別途決める必要がある。KEN-29が挙げた対応案は次の3つで、いずれも決定ではなく列挙のみ
  （新しい検証機構の追加を伴うため人間の合意、場合によってはADRが要る。P-05・P-08）。
  1. アプリ層での自前計測: 既存のgunicornアクセスログ方式（`DEPLOYMENT.md` §3-3）を延長し、
     DBへの最初のクエリのレイテンシをリクエストログに記録する。Neonのcompute grafを見る方式
     （既に失敗し禁止済み）とは別の観測点であり、既存の禁止事項には抵触しない。
  2. Neonの使用量集計API/コンソールで、時系列グラフではなく累計値（CU時間・容量）を取得する経路を
     調べる。禁止されているのは粗い時間分解能によるイベント検出の用途であり、累計消費量の確認は
     別の問題である可能性があるが、外部アクセスができないため要検証。
  3. 何もしない（既知の未知として抱える）: `adr/0021`帰結が既に持つセーフティネット（無料条件が
     変わった場合は費用発生前に停止し再判断する）を根拠に、観測手段が無いことを構造的リスクとして
     明記した上で新たな検証機構を追加しない、という消極的選択。P-05と整合する。

## 決定

**本ADRは決定を下さない。status: 提案中のまま、比較材料と未決論点の記録に留める。**
3選択肢はいずれも推奨として残す。どれを選ぶべきかは、以下の人間の判断（特に予算上限と許容できる
移行作業量）に依存し、その判断が下されるまで本ADRを承認済みにすることはできない。

参考として、KEN-29が示した条件付きの絞り込みを記録する（決定ではなく、条件が満たされた場合に
どの選択肢が有力になりやすいかの整理）。

- 項目8（観測手段の欠如）を最優先で解消したい場合: 選択肢1・2のうち、DB側で常時起動のRDS for
  PostgreSQLを選ぶ組み合わせが、scale-to-zero自体を発生させなくすることで問題を構造的に消滅させる。
  Web側を変える必要は必須ではないため、移行コストを抑えたいなら選択肢2が有力。
- 項目3（Render 750h上限）も含めて解消したい場合: 選択肢1が必要になるが、移行コスト・運用負荷・
  費用が最大になる。
- 費用ゼロの維持を最優先する、または移行作業量を割けない場合: 選択肢3を維持しつつ、上記の項目8への
  対応案のどれを取るか（または何もしないか）を人間が決める必要がある。

いずれの場合も、AWS側の「無料枠」の恒久性・条件（Neonの無期限無料枠とは性質が異なる可能性が高い）を
検証しないまま費用比較をすることはできない。

### 人間が選ぶ必要がある論点（KEN-29より）

1. **予算上限**: 固定費・従量費を許容するか、無料運用の継続を最優先するか。許容する場合、月額の
   どの桁までが許容範囲か。
2. **許容できる移行作業量・停止リスク**: 選択肢1のCI/CD総入れ替え、選択肢2のDB移行（ダウンタイム・
   切替手順）をどこまで許容するか。
3. **選択肢2を取る場合のネットワーク公開方針**: RDS/Auroraをpublicly accessibleにするか、Renderの
   送信元IPでの許可リストが技術的に可能か（要検証、本ADRでは未確認）。
4. **選択肢1を取る場合の静的配信アーキテクチャ**: アプリコンテナからの同一オリジン配信を維持するか、
   S3/CloudFront等へ切り出すか（切り出す場合は`adr/0010`の同一オリジンvendoring規約を満たす追加
   設計が要る）。
5. **Aurora Serverless v2のpause/resume相当機能を使うかどうか**: 使うと項目8と同種の「粗い観測手段
   しかない」問題が再発し得るため、使うか使わないかは人間の判断が要る。
6. **選択肢3を取る場合、項目8への対応案（上記1〜3）のどれを採るか**: 新しい検証機構の追加はP-05・
   P-08に照らして人間の合意（場合によってはADR）が要る。「何もしない」も正当な選択肢として残っている。
7. **ECS Fargate選択時にECS Execを使ってSSH相当のアクセスを持つかどうか**: 現状「SSH無し」は問題
   視されていない（`adr/0021`決定6が既にその前提で運用設計を組んでいる）ため、これは既存の問題を
   解くためではなく、新たな運用上の選択肢として持つかどうかの判断になる。

## 帰結

- 本ADRは`status: 提案中`のまま残る。人間が上記7論点のうち必要なものに答え、3選択肢のいずれかを
  選ぶ（または選択肢3＋対応案という組み合わせを選ぶ）までは、**承認は成立せず、現行構成
  （`adr/0021`の無料Render Web + 無料Neon Postgres）が変更されずに続く**。
- 項目8（Neon 5分scale-to-zeroの観測手段の欠如）は、本ADRが承認されない限り未解消のまま残る。
  この状態は新しいリスクではなく、`adr/0021`帰結が定めたセーフティネット（無料条件が変わった場合は
  費用発生前に停止し再判断する）の範囲内で、KEN-28が可視化した既存のギャップである。
- 項目3・6・7（Render月750h・Neon CU時間・Neon容量）の実測は、本ADRの決定とは独立に、いずれの
  選択肢を選ぶ場合でも別途必要になる作業として残る。
- 新しい規程・契約・実装コードはいずれも本ADRの対象外であり、変更しない。将来この比較を踏まえて
  移行を決定するADRは、本ADRをsupersedeする形で起票する。
