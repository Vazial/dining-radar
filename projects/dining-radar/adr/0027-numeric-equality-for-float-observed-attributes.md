# ADR-0027: この契約で浮動小数点フィールドを機械観測する属性は、数値としての一致を既定にする

> **承認者向けサマリ**: `candidate-search-browser-interface.yaml` の `searchOriginMarker.positionAttributes`
> （`adr/0025` 2026-08-24 追記が FR-022(1) を塞ぐために新設）を実装・tester のstepへ通したところ、L4が
> 1件落ちた。JavaScript の `String(0.0)` は `"0"`、Python の `str(0.0)` は `"0.0"` であり、**同じ数値
> でも言語によって10進表記が異なる**。契約の `presenceRule` は「exact canonical decimal string」と
> 書いていたが canonical の定義を持たず、前例の `cardDataAttributes.rawValueAttribute`（文字列一致）は
> 整数・閉じた enum 文字列にしか使われておらず、浮動小数点には届いていなかった。本ADRは、この契約で
> 今後 float 型フィールドを機械観測する属性を追加するときの既定規則を決める——**数値として比較する。
> 契約が明示的に canonical な文字列書式を定義しない限り、文字列一致を既定にしない。**

## 文脈

`friction-log` の FR-022 は、契約が検証を要求しながらその検証を成立させる事実を持っていない欠落の型を
記録している。(1) 位置を読む属性が無い、(2) 承認済み配置のもとでマーカーに到達できない、に続き、本件
（数値の文字列表現差）が3件目である——**(1) を塞ぐために足した属性の等価規則自体が、言語依存の書式差で
崩れた**。FR-022 は「2回では仕組みを入れるほどの確度がまだ無い」と判断して仕組み化を見送ったが、
「3回目が出たときにADRを起こす」と明記していた。本ADRはその約束を実施する。

3件はいずれも異なる技術的形（属性の不在、幾何の重なり、数値の文字列表現差）を取っており、それらを
すべて防ぐ単一の機械検査は現実的でない——「契約を書き漏らすな」は機械で強制できる規則ではない。本ADRが
決めるのは、直接原因が特定できた本件（数値の文字列表現差）に限定した、狭い契約規約である。

## 決定

1. `candidate-search-browser-interface.yaml` で、JSON Schema 上 `number` 型（整数ではない浮動小数点）
   のフィールドを機械観測する属性を新設する場合、既定の等価規則は**数値比較**とする——属性の文字列を
   数値へ解析し、応答値との差が契約が定める許容誤差以内であることを検証する。許容誤差は各観測ごとに
   明示する（`searchOriginMarker.positionAttributes` は 1e-9 度）。
2. `cardDataAttributes.rawValueAttribute` の文字列一致様式は、整数値（`totalSeats`）と閉じた enum
   文字列（`nonSmokingStatus`・`dinnerBudgetTier`）に対してはそのまま維持する——これらは正準な表記が
   一意に決まる値であり、本ADRの対象外である。
3. 文字列としての canonical 書式を契約で定義する案（例:「応答JSONに現れる表記そのまま」「小数点以下を
   必ず1桁以上持つ」）は、両側の実装がその書式規約を守っているかを機械で検査する術がなく、FR-022(1)
   が塞いだのと同じ「検証できないことを検証せよ」という契約を作り直すだけになるため、この契約では
   採らない。数値比較では証明できない性質（例えば「応答のバイト列と属性の文字列が完全に一致する」こと
   そのものを検証したい場合）が具体的に生じたときに、個別のADRで再検討する。

## 検討した代替案

- **数値としての一致に変える（採用）**: presenceRule が実際に必要とする性質——マーカーの位置が
  `response.searchOrigin` に由来し、独立に知られた定数ではないこと——は数値としての同一性であって
  字面の同一性ではない。IEEE 754 の同じ値でも言語ごとに複数の妥当な10進表記があるため、数値比較は
  言語間の表記差に依存しない。
- **canonical な文字列形式を契約で定める**: 不採用（決定3）。様式（文字列一致）は保てるが機械検査の
  術がなく、実装責任での一致に後退する。
- **属性の値を、応答のJSONに現れる文字列そのものにする**: 不採用。サーバ側で数値ではなく生のJSON表記
  を別途保持し、ブラウザ側も `JSON.parse` を経由せずその文字列をそのまま属性へ運ぶ実装変更が要る。
  得られる保証は数値比較と実質的に同じであり、追加のコスト（標準のJSONパース経路を迂回する実装、将来
  のサーバ側シリアライズ方式変更への脆弱性）に見合わない。

## 私の切り分け（meta/adr/0047）

本ADRは `candidate-search-browser-interface.yaml` という**この契約自身**の等価規則を決めるものであり、
プロジェクト scope の ADR として起草する。architect はこの権限を持つ（`meta/adr/0047`——「プロジェクト
の契約の中身・設計骨格を決めるADRはarchitectの領分」）。

**本ADRは書かない、orchestrator（`meta/adr/0047`）に判断を委ねる論点**: cause_key
`l4-browser-observation-contract-missing` が3回出たという事実そのもの（friction-log 横断の再発検知、
`meta/adr/0058`）は、この契約に閉じない一般的な摩擦の観測である。テンプレート全体として「契約が検証を
要求するが検証の手段を持っていない」という欠落の型を、機械/運用でどこまで先回りして防ぐかは、architect
の契約起草判断を超えたガバナンスの論点である。3件の技術的形がそれぞれ異なる（属性の不在・幾何の重なり・
数値表現差）ため、単一の一般的機構が有効かどうかも自明ではない。この判断は orchestrator へ委ねる。

## 2026-08-24 追記2（architect、独立監査F1・FR-022の4回目への対応。決定本文は書き換えない）

独立監査（`reviews/audit-tdr-cs-origin-marker-position.md`、F1）が Blocker を1件報告した。決定1に沿って
数値比較へ改めた `presenceRule` の「マーカーの位置が応答の `searchOrigin` に由来し、**独立に知られた
定数ではない**ことを証明する」という主張を、**実際にはテストが証明できていなかった**。原因は
`src/dining_radar/suggestions/acceptance_state.py:196` の `_ORIGIN = Origin(latitude=0.0, longitude=0.0)`
が全14箇所・全モードで共有されており、acceptance が返す `searchOrigin` が常に `(0.0, 0.0)` だったこと
である。したがって「応答を正しく読む実装」と「`0`/`0`を決め打ちする実装」が常に同じ結果になり、
応答とDOM属性の突き合わせ（自己整合性チェック）ではこの2つを区別できない。

**契約2本が食い違っていた。** `candidate-search-browser-interface.yaml` の `presenceRule` は「fixture-baked
value ではないことを証明する」と強く主張する一方、`contracts/test-support-api.yaml`（2026-08-20起草の
該当箇所）は「`searchOrigin` の値そのものを Given API で選択可能にする必要はない。自己整合性だけを
検証すれば足りる」と明示的に弱く主張していた。後者が先に書かれ、前者（`positionAttributes`、
2026-08-24）が後から強い主張を足した形になっており、前者を足した時点でこの矛盾を確認しなかった。

**塞ぎ方は (a) を採った**（コーディネータが提示した3択のうち）——`test-support-api.yaml` の
`CandidateProposalAcceptanceState` に任意プロパティ `searchOrigin`（nullable、緯度経度）を新設し、
Given がテスト自身の選んだ値を送れるようにした。省略時は従来どおりの合成定数を返し、既存シナリオの
挙動は無変更のまま保つ（後方互換）。あわせて、`searchOrigin` の値そのものを選択可能にする必要はないと
書いていた誤った記述を、この新プロパティの説明に置き換えた。

**(b)（モードごとに異なる合成基点を返す）は不採用。** コーディネータの指摘どおり、これは「どのモードが
どの値を返すか」というテスト側の暗黙知識を要求し、モードを追加するたびにこの知識を保守する負担を生む。
`randomSeed` が既に確立している「Given状態の1軸としてモードから独立に選択可能にする」という様式（本
契約の既存の設計原則）を素直に踏襲する (a) の方が、将来のGiven追加にも一般化できる。

**(c)（presenceRuleの主張を弱める）は不採用。** コーディネータの指摘のとおり、これを採ると FR-022 が
指摘した欠陥（検証手段のない検証要求）を、「検証できていないのに検証したと書く」という**より悪い形**で
残すことになる。`presenceRule` が本当に証明したい性質（応答由来であり独立に知られた定数ではないこと）
は製品として意味のある性質であり、証明する手段（(a)）が存在する以上、主張を下げる理由がない。

### FR-022 の cause_key、4件目を見た見立ての変化

4件はそれぞれ (1) 属性が無い、(2) 承認済み配置のもとで要素に届かない、(3) 数値の文字列表現が言語で
異なる、(4) **検証しているつもりで検証できていなかった**、である。`adr/0027` 起票時点（3件目まで）の
私の見立ては「3件はいずれも異なる技術的形を取っており、単一の機械検査は現実的でない」だった。**この
見立ては、4件目を踏まえて部分的に修正する。**

(1) と (4) は、技術的な現れ方は異なる（前者は観測手段の不在、後者は観測手段はあるがそれを裏付ける
データの多様性の不在）が、**同じ種類の主張の失敗**である——presenceRule・invariant が「この値は独立に
知られた定数ではない」「fixture-baked value ではない」という形の主張をするとき、その主張が成立するには
(i) 値を読み取る観測可能な属性が存在すること、**かつ** (ii) その値を裏付ける Given データが、少なくとも
その主張を検証する対象のシナリオにおいて、実装が決め打ちでは通せない形で変動すること、の**両方**が要る。
(1) は (i) の欠如、(4) は (ii) の欠如だった。(2)・(3) はこの「独立に知られた定数ではない」という主張の
族には属さない、別種の欠落（幾何の重なり、数値表現の言語差）である。

したがって、**「単一の機械検査は現実的でない」という結論は変えない**——(2)・(3) は依然として別の技術的
形であり、4件全体を横断する機械検査を今回のために新設する根拠にはならない。**変えるのは範囲である**:
「独立に知られた定数ではない」「fixture-baked value ではない」という**特定の言い回しの主張族**に限れば、
(i)・(ii) の両方を確認するという具体的で狭い執筆時チェックリストが今回はっきりした。これは機械検査
ではなく、architect が今後この種の主張を契約に書く際の**自己点検項目**として運用する——同じ族の主張が
5件目・6件目と続けば、その時点でこの狭い族に限定した機械検査（例えば govlint が「independently known
constant」「fixture-baked」等の語を含む presenceRule を検出し、対応する Given がモード非依存に値を
選択可能かを人間に確認させる）を検討する材料になる。今回時点ではまだ導入しない（P-05）——執筆時の
自己点検で今回の形は防げたはずであり、機械化の前に運用（自己点検）で十分か見る余地がある。

cause_key `l4-browser-observation-contract-missing` の一般論（テンプレート全体でこの種の欠落をどこまで
先回りして防ぐか）は、引き続き orchestrator（`meta/adr/0047`）に委ねる——4件目が加わっても、この判断を
architect が単独で下せる材料が増えたわけではない。
