# ADR-0027: この契約で浮動小数点フィールドを機械観測する属性は、数値としての一致を既定にする

> **承認者向けサマリ**: `candidate-search-browser-interface.yaml` の `searchOriginMarker.positionAttributes`
> （`adr/0025` 2026-08-24 追記が FR-022(1) を塞ぐために新設）を実装・tester のstepへ通したところ、L4が
> 1件落ちた。JavaScript の `String(0.0)` は `"0"`、Python の `str(0.0)` は `"0.0"` であり、**同じ数値
> でも言語によって10進表記が異なる**。契約の `presenceRule` は「exact canonical decimal string」と
> 書いていたが canonical の定義を持たず、前例の `cardDataAttributes.rawValueAttribute`（文字列一致）は
> 整数・閉じた enum 文字列にしか使われておらず、浮動小数点には届いていなかった。本ADRは、この契約で
> 今後 float 型フィールドを機械観測する属性を追加するときの既定規則を決める——**数値として比較する。
> 契約が明示的に canonical な文字列書式を定義しない限り、文字列一致を既定にしない。**

## 文脈

`friction-log` の FR-022 は、契約が検証を要求しながらその検証を成立させる事実を持っていない欠落の型を
記録している。(1) 位置を読む属性が無い、(2) 承認済み配置のもとでマーカーに到達できない、に続き、本件
（数値の文字列表現差）が3件目である——**(1) を塞ぐために足した属性の等価規則自体が、言語依存の書式差で
崩れた**。FR-022 は「2回では仕組みを入れるほどの確度がまだ無い」と判断して仕組み化を見送ったが、
「3回目が出たときにADRを起こす」と明記していた。本ADRはその約束を実施する。

3件はいずれも異なる技術的形（属性の不在、幾何の重なり、数値の文字列表現差）を取っており、それらを
すべて防ぐ単一の機械検査は現実的でない——「契約を書き漏らすな」は機械で強制できる規則ではない。本ADRが
決めるのは、直接原因が特定できた本件（数値の文字列表現差）に限定した、狭い契約規約である。

## 決定

1. `candidate-search-browser-interface.yaml` で、JSON Schema 上 `number` 型（整数ではない浮動小数点）
   のフィールドを機械観測する属性を新設する場合、既定の等価規則は**数値比較**とする——属性の文字列を
   数値へ解析し、応答値との差が契約が定める許容誤差以内であることを検証する。許容誤差は各観測ごとに
   明示する（`searchOriginMarker.positionAttributes` は 1e-9 度）。
2. `cardDataAttributes.rawValueAttribute` の文字列一致様式は、整数値（`totalSeats`）と閉じた enum
   文字列（`nonSmokingStatus`・`dinnerBudgetTier`）に対してはそのまま維持する——これらは正準な表記が
   一意に決まる値であり、本ADRの対象外である。
3. 文字列としての canonical 書式を契約で定義する案（例:「応答JSONに現れる表記そのまま」「小数点以下を
   必ず1桁以上持つ」）は、両側の実装がその書式規約を守っているかを機械で検査する術がなく、FR-022(1)
   が塞いだのと同じ「検証できないことを検証せよ」という契約を作り直すだけになるため、この契約では
   採らない。数値比較では証明できない性質（例えば「応答のバイト列と属性の文字列が完全に一致する」こと
   そのものを検証したい場合）が具体的に生じたときに、個別のADRで再検討する。

## 検討した代替案

- **数値としての一致に変える（採用）**: presenceRule が実際に必要とする性質——マーカーの位置が
  `response.searchOrigin` に由来し、独立に知られた定数ではないこと——は数値としての同一性であって
  字面の同一性ではない。IEEE 754 の同じ値でも言語ごとに複数の妥当な10進表記があるため、数値比較は
  言語間の表記差に依存しない。
- **canonical な文字列形式を契約で定める**: 不採用（決定3）。様式（文字列一致）は保てるが機械検査の
  術がなく、実装責任での一致に後退する。
- **属性の値を、応答のJSONに現れる文字列そのものにする**: 不採用。サーバ側で数値ではなく生のJSON表記
  を別途保持し、ブラウザ側も `JSON.parse` を経由せずその文字列をそのまま属性へ運ぶ実装変更が要る。
  得られる保証は数値比較と実質的に同じであり、追加のコスト（標準のJSONパース経路を迂回する実装、将来
  のサーバ側シリアライズ方式変更への脆弱性）に見合わない。

## 私の切り分け（meta/adr/0047）

本ADRは `candidate-search-browser-interface.yaml` という**この契約自身**の等価規則を決めるものであり、
プロジェクト scope の ADR として起草する。architect はこの権限を持つ（`meta/adr/0047`——「プロジェクト
の契約の中身・設計骨格を決めるADRはarchitectの領分」）。

**本ADRは書かない、orchestrator（`meta/adr/0047`）に判断を委ねる論点**: cause_key
`l4-browser-observation-contract-missing` が3回出たという事実そのもの（friction-log 横断の再発検知、
`meta/adr/0058`）は、この契約に閉じない一般的な摩擦の観測である。テンプレート全体として「契約が検証を
要求するが検証の手段を持っていない」という欠落の型を、機械/運用でどこまで先回りして防ぐかは、architect
の契約起草判断を超えたガバナンスの論点である。3件の技術的形がそれぞれ異なる（属性の不在・幾何の重なり・
数値表現差）ため、単一の一般的機構が有効かどうかも自明ではない。この判断は orchestrator へ委ねる。

## 帰結

- `candidate-search-browser-interface.yaml`（`1.3.2`）の `searchOriginMarker.presenceRule` を、本ADR
  決定1に沿って数値比較へ改めた（本ADRと同じコミットで実施済み）。
- `friction-log.md` の FR-022 に、本ADRを参照する追記を行う。
- 実装・テストの変更はこの改訂だけでは完結しない——developer は `candidate.js` の実装（既に
  `String(searchOrigin.latitude/longitude)` で属性を設定済みであり、この決定のもとでは変更不要である
  可能性が高いが、確認は developer の領分）、tester は step 定義を文字列比較から数値比較（許容誤差
  1e-9 度）へ書き換える必要がある。
