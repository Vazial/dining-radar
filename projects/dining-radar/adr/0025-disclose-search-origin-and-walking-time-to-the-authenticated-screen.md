# ADR-0025: 検索基点と徒歩時間を認証済み画面に表示し、徒歩の上限を絞り込み条件の一つとして扱う

> **承認者向けサマリ**: `ADR-0008` 決定4 は「正確な検索基点・設定範囲を browser、公開 URL、ログ、
> エラー、trace、Git に出さない」ことを Must と定めた。本ADRはこのうち **browser への非開示だけを
> 撤回する**。人間裁定 2026-08-20 chat: 『別にソースから現在位置を推測できなければいいから、環境変数で
> 指定すればよく、アプリ利用者にはバレてもいい（というか利用者全員がそのへんにいるから徒歩圏内が成立
> するわけだし）』。**(1)** 認証済み候補画面は検索基点をマーカーとして表示し、そこを中心とする徒歩圏の
> 同心リングを描いてよい。**(2)** 候補カードは徒歩時間を表示してよい。**(3)** 徒歩の上限を
> `CandidateFilters` の一条件として扱い、「上限を15分にすると+2件」が他の絞り込み条件とまったく同じ形で
> 提示されるようにする。**(4)** 検索基点の実座標は環境変数で与え、Git には置かない——`ADR-0002` と
> `product-brief.md` §4 の公開リポジトリ境界は**一切変更しない**。**(5)** タイル提供者へ基点を渡さない
> `Referrer-Policy`（`ADR-0008` 決定5）は維持する。**(6)** ブラウザの位置情報（現在地）と徒歩**経路**は
> 引き続き扱わない。同心リングの半径から設定探索範囲が間接的に推測されうることは**許容する**（決定9、
> 人間裁定 2026-08-20）——許容するのは推測可能性であって、値そのものの露出ではない。**(7)** 本決定は
> `ADR-0004` 決定2 の該当句と `ADR-0008` 決定4 のうち browser に
> 関する部分を改め、`product-brief.md` §1・§3 の該当行の改訂を要求する。既承認文書の改訂を伴うため、
> 承認は `ADR-0035` 方式(ii)に倣い、衝突する文書の改訂が同一PRで成立することを条件とする。

## 文脈

### 0. 検証の申告（meta/adr/0039）

本ADRが「徒歩時間を返せる」と述べる根拠は、`contracts/candidate-search-api.yaml` の `Candidate.location`
が緯度経度を返しており、検索基点がサーバーの非公開設定として既に存在することである。ここまでは既存の
契約と実装から確認した。**確認していないのは徒歩時間の算出方式である**——直線距離からの推定なら追加の
外部通信は不要だが、道のり基準にするには経路データ源が要る。issue #104 の探索ラフは「徒歩時間は直線
距離ではなく道のり基準」を前提として描かれていたが、その前提を満たす手段は本ADRでは選定していない。
決定2はこの点を明示的に実装判断へ送る（帰結を参照）。

### 1. 何が変わったか

`ADR-0004` は「地図に検索基点・徒歩ルート・現在地を加える」案を、**生活圏の露出と外部通信を増やす**
という理由で却下した。`ADR-0008` 決定4 はこれを Must として固定し、`product-brief.md` §1 は「検索基点は
サーバーの非公開設定にある1地点で、ブラウザから入力も表示もしない」、§3 は「検索基点、検索基点マーカー、
徒歩経路、現在地、徒歩時間は表示しない」と書いた。

却下理由の前半——生活圏の露出——は、**露出先を特定していなかった**。この製品の画面を開けるのは
`ADR-0006` の招待制認証を通った幹事だけであり、公開サインアップは存在しない。そして幹事は全員が基点の
界隈で働いている——だからこそ「徒歩圏の店を比べる」という製品の中心概念が成立している。基点を知らない
読み手が画面の向こうに存在しないため、隠す対象がない。

却下理由の後半——外部通信——は、対象を分ければ**なお有効である**。徒歩**経路**（ルート線）は外部の
経路探索サービスへの問い合わせを要する。一方、基点マーカーと同心リングは既知の2点だけで描け、徒歩時間も
サーバーが基点と候補座標から自分で算出できる。前者は却下したまま、後者だけを採る。

Git への非開示は、この検討とは**独立に有効である**。実座標・地名・既定探索距離を公開リポジトリに
置かないという `ADR-0002` と `product-brief.md` §4 の制約は provider 規約とも利用者とも無関係な判断で
あり、環境変数による供給がそれをそのまま満たす。

### 2. 表示しないことで失われていたもの

候補一覧は既に近い順に並んでおり、**順位は相対的な近さを伝えている**。徒歩時間が足すのは絶対的な
スケールである。1位が徒歩3分なのか徒歩12分なのかは、昼休みに往復で18分の差になり、幹事の判断を変える。
現行画面はこの情報を完全に落としている。

`ADR-0022` が導入した `populationAttributes` は「保留中の絞り込みが何件に効くか」をブラウザ側で数える
ための匿名属性表である。徒歩の上限をこの枠組みに乗せると、「徒歩の上限を15分にすると +2件」が
「禁煙席ありを外すと +4件」とまったく同じ形で並ぶ。距離だけを専用の仕掛けで扱う必要がなくなる。

## 決定

1. 認証済み候補画面は、検索基点をマーカーとして表示する。地図は基点を中心とする徒歩圏の同心リングを
   描く。地図は引き続き `ADR-0010` の同一オリジン Leaflet と OpenStreetMap 標準タイルだけを使う。
2. `POST /candidate-proposals` の応答は候補ごとの徒歩時間を返し、カードはこれを表示する。
   徒歩時間は**推定であり実測経路ではない**ことを、値の提示が断定に読めない形で扱う。算出方式（直線距離
   からの推定か、道のり基準か）と、道のり基準を採る場合のデータ源は実装スライスで選定し、外部通信を
   増やす選択をする場合は本ADRとは別に判断する。
3. 徒歩の上限を `CandidateFilters` の一条件として扱う。他の絞り込み条件と同じく `applied` と `pending`
   を分け、`populationAttributes` に基づく件数予告の対象とする。`populationAttributes` に距離帯を
   加える場合も、行が店舗を同定しない性質（`ADR-0022`）を壊してはならない——距離帯は粗い区分として
   加え、候補との対応順序を持たせない。
4. 検索基点の実座標・既定探索距離は環境変数で与える。`ADR-0002` の公開リポジトリ境界と
   `product-brief.md` §4 は**変更しない**。リポジトリ内の設計資料・スクリーンショット・
   `design-preview` は引き続き合成座標だけを使う。
5. `ADR-0008` 決定5 の `Referrer-Policy: strict-origin-when-cross-origin` を維持する。基点をタイル
   提供者へ渡さない境界は、利用者への開示とは無関係に必要である。
6. ブラウザの位置情報（現在地）と徒歩**経路**の描画は引き続き行わない。前者は利用者本人の実時間の
   居場所であり基点とは別種の情報である。後者は `ADR-0004` の却下理由のうち外部通信の側がなお当たる。
7. 本決定は `ADR-0004` 決定2 の「検索基点、基点マーカー、徒歩経路、現在地、徒歩時間は返さず表示しない」
   のうち、基点・基点マーカー・徒歩時間に関する部分と、`ADR-0008` 決定4 のうち browser への非開示に
   関する部分を改める。**公開 URL・ログ・エラー・trace・Git への非開示は改めない。**
8. `product-brief.md` §1（検索基点は「ブラウザから入力も表示もしない」）と §3（「検索基点、検索基点
   マーカー、徒歩経路、現在地、徒歩時間は表示しない」「ブラウザへ渡す位置情報は候補店舗の位置だけと
   し、非公開の検索基点は送らない」）を、本ADRに合わせて改訂する。入力は環境変数のままで、変わるのは
   表示だけである。
9. 設定探索範囲が同心リングの半径から**間接的に推測されうることを許容する**。リングの本数・半径の
   選び方に制約は置かない（人間裁定 2026-08-20 chat）。基点そのものを開示すると決めた以上、同じ
   読み手から探索範囲だけを隠す理由がない。**ただし許容するのは間接的な推測可能性であって、値の
   直接的な露出ではない**——設定探索範囲の値そのものを API 応答・DOM・公開 URL・ログ・trace へ
   出さないという既存の Must は維持し、決定4 の Git 非開示も無変更である。

## 検討した代替案

- **粗い距離帯（3段階）だけを出す**: 基点を出さない前提のもとで三辺測量による基点逆算を防ぐための妥協案
  として検討した。**不採用**——その前提自体が本ADRで撤回されるため、粗くする理由が消える。逆算を心配
  しなくてよいなら、昼休みの判断に効くのは正確な分数のほうである。
- **現状維持（徒歩情報を出さない）**: **不採用**。近い順の順位は相対的な近さしか伝えず、絶対的な
  スケールが利用者に届かない。
- **徒歩経路（ルート線）も描く**: **不採用**。外部の経路探索サービスへの通信が増え、`ADR-0004` の
  却下理由の後半がそのまま当たる。
- **基点を幹事がブラウザから設定できるようにする**: **不採用（本ADRの範囲外）**。表示と入力は別の
  判断であり、入力を開くと会ごとに異なる基点・在宅拠点といった別の設計課題が付随する。本ADRは表示だけを
  扱い、入力は環境変数のまま据え置く。

## 帰結

- `product-brief.md` §1・§3 の改訂が要る。`ADR-0035` 方式(ii)に倣い、本ADRの承認はその改訂が同一PRで
  成立することを条件とする。§4 の公開リポジトリ境界は無変更のまま残る。
- `contracts/candidate-search.feature` と `contracts/candidate-search-api.yaml` の改訂が要る。徒歩上限
  フィルタの追加、候補への徒歩時間フィールドの追加、`Candidate` の description にある「基点・徒歩時間を
  返さない」旨の記述の改訂、`populationAttributes` の禁止属性列から徒歩時間・距離を外すかの判断が含ま
  れる。既存の `TDR-CS` シナリオのうち、基点非表示を観測しているものは改訂対象になる。
- 実装は距離計算をサーバー側に持つ。provider は候補座標を返すため、**直線距離からの推定を採る限り**
  追加の外部通信は発生しない。道のり基準を採る場合は経路データ源の選定が別途要る（決定2）。
- `ADR-0020` の L5 レンダー不変条件のうち、内部enum非露出と44px最小サイズは徒歩上限コントロールにも
  適用される。徒歩上限のコントロールは既存フィルタと同じ扱いになる。
- 公開リポジトリに置く設計資料は引き続き合成座標を使う。本ADRはリポジトリ側の運用を何も緩めない。
- `projects/toyama-dining-radar/` というプロジェクト名に含まれる実在の地名は、§4 の「地名を Git に
  置かない」に照らすと本ADRとは独立の未解決事項である。本ADRはこれを扱わない。
