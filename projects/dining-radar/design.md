# design.md — Dining Radar 設計骨子

> **承認者向けサマリ**: 非公開のruntime検索条件から店舗候補と代替候補を得るDjangoモノリスの設計骨格である。外部provider連携と候補の適格性判定・順位付けを分離し、公開Gitにはschema migrationと合成fixtureだけを置く。この製品は実データの長期保存、利用履歴、ブラックリストを持たない。

## スコープ

このfoundationは、非公開のruntime検索条件で外部候補を探し、候補と代替候補を示すための責務分割だけを定める。この製品は利用済み・ブラックリストを実装せず、同じ画面で既に表示した候補を再提案時に二次的に順位低下させる。この降格はサーバが再提案リクエストごとに行い、ブラウザは同一画面内で見せられた候補のURLをそのリクエストへ送るだけで、サーバはそれを保存しない（ADR-0017。ADR-0008決定2を置き換える）。画面、endpoint、DB schema、API接続、認証情報、実データは定めない。候補提案の現在の画面・APIの振る舞いは、ADR-0005とcandidate-search契約が定める。

候補提案は、管理者が作成した有効な個別幹事 account の same-origin Django session だけに開く。公開signup、
メールreset、SSOは初期スコープにない。認証・公開運用の状態と設定境界は ADR-0006、
`contracts/authentication.feature`、`contracts/authentication-api.md` が定める。ここでは認証画面、
管理画面、host、domain、email、session expiryの具体を定めない。

## 処理の流れ

```text
runtime検索条件
  -> Hot Pepper adapter
  -> provider形式を内部候補へ正規化
  -> 既定では、ランチ営業の実施が確認しづらいジャンル（居酒屋・バー等）を候補母集団から除く。
     含める切り口を選んだときだけ、そのジャンルも母集団に含める（ADR-0015）
  -> 順位付け（除外後、または含めた場合はその、母集団全体に対して行う）
  -> 再提案リクエストでは、幹事のブラウザが同じ画面内で以前に見せられた候補のprovider page URLを
     送ってきた場合、順位を保ったまま既表示候補を後方へ二次順位低下させる（ADR-0017。初回表示では
     この一覧は空であり、無効果）
  -> 順位付け（・降格）後の上位5件を切り口の候補として選ぶ（ADR-0015。表示上限であり、取得・順位付け
     対象の上限ではない）
  -> 候補と代替候補の提示（必要なcreditを併記）
```

候補の複数人利用可否や予約可否は、providerが返す参考情報であり保証しない。providerの店舗事実は変更せず、アプリ側は選択・除外・順序付けのみを行う。総席数の目安（`capacityTier`）、予算感の目安（`dinnerBudgetTier`）、カード払いに関する注意（`cardPaymentAvailable`が`false`の時だけ表示）はカードの表示専用の派生値であり、順位付けには関与しない（ADR-0019）。

## 候補提案の画面投影

```text
サインイン済みの幹事が候補提案画面を開く
  -> 一つの初期切り口による候補カードと店舗だけの地図を表示
  -> カードとマーカーを相互に強調して比較
  -> 「別の切り口で再提案」を選ぶ
  -> 最大3つの次の切り口をモーダルで表示
  -> 一つを選ぶと直ちに新しい候補提案が依頼される（確認のための追加操作はない。ADR-0016）
  -> 新しい候補提案でカード・地図全体を置き換える
  -> 同じ画面で既に表示した候補は未表示候補より後ろに表示する

（別経路）
サインイン済みの幹事が「もう一度探す」を選ぶ（ADR-0016）
  -> 現在表示中の切り口のまま新しい候補提案を依頼する
  -> 新しい候補提案でカード・地図全体を置き換える
  -> 同じ画面で既に表示した候補は未表示候補より後ろに表示する
  -> 新しい候補が以前とすべて異なる店舗になるとは限らない
```

（いずれの経路でも）既に表示した候補より後ろへ置く二次順位低下は、ブラウザが送る既表示候補の
provider page URL一覧をもとにサーバが行う。ブラウザはこの一覧を同一画面のメモリだけに保持し、
再提案のたびにそのリクエストへ含めるが、保存はしない（ADR-0017。ADR-0008決定2を置き換える）。

初期表示では検索範囲・ジャンルなどの補助条件やコンセプト選択を置かない。切り口の選択は再提案時だけであり、候補を追加表示しない。同じ画面では、既表示候補を除外せず未表示候補より後ろへ置く。この比較状態（既表示候補のprovider page URL一覧）はブラウザ内のメモリだけに保持され、更新・タブを閉じる・サインアウトで消える。再提案のたびにこの一覧をサーバへ送るが、サーバはその1リクエストの候補選定にだけ使い、保存しない（ADR-0017）。地図には候補店舗だけを出し、検索基点・経路・現在地・徒歩時間を出さない。詳細な受け入れ状態とbrowser-facing APIは `contracts/candidate-search.feature` と `contracts/candidate-search-api.yaml` を参照する。

「もう一度探す」は、別の切り口を選ぶ操作とは異なる。独自の順位付け基準を持つ切り口（コンセプト）ではなく、現在表示中の切り口をそのまま使って新しい提案を依頼するだけの操作であり、新しい候補が現れるかどうかは、既表示候補の二次的な順位低下だけに依存する（乱数や決定性の緩和は行わない。ADR-0016）。この降格はサーバが再提案リクエストごとに行う（ADR-0017）。2度目の実データレビューで、切り口の一つ（ジャンルを横断して比較する切り口）が実データ上ほぼ常に初期切り口と同一の候補・順序へ縮退することが判明し、その切り口を廃止して「もう一度探す」に置き換えた。3度目の実データレビューでは、表示上限5件（ADR-0015）が既にこの降格の機能条件を崩していたこと自体が判明し、降格の実施箇所をブラウザからサーバへ移した（ADR-0017）。

各切り口の候補は最大5件まで表示する（ADR-0015）。順位付けは取得・正規化した母集団全体に対して行い、5件は表示段階だけに適用する表示上限であって、取得・順位付け対象の上限ではない。ランチ営業の実施が確認しづらいジャンル（居酒屋・バー等）は既定の母集団から除き、幹事が「居酒屋・バーを含めて探す」といった切り口を再提案の選択肢として選んだときだけ母集団に含める。この除外は「確認できないランチ営業実態を確定的な事実として断定しない」という判断であり、検索範囲・ジャンルの補助的な絞り込み（初期表示・再提案時に幹事が任意の値を入力・選択することの禁止）とは異なる——幹事は任意の値を入力・選択するのではなく、あらかじめ用意された説明可能な切り口の一つを選ぶだけであり、この点は他の切り口と同じ操作である。除外の結果すべての切り口が説明不能になる場合は、除いていたジャンルも含めた母集団で提案する（このとき「条件に合う候補がない」という案内には切り替えない）。

切り口（コンセプト）は現在4種類（`PROXIMITY`・`GENRE_FOCUS`・`NON_SMOKING_REFERENCE`・
`IZAKAYA_BAR_INCLUDED`）であり、再提案の選択肢は表示中の1つを除いた残りである。この数の関係
（切り口の総数−表示中の1つ）は、再提案の選択肢の表示上限（3つ以下）に常に収まる（ADR-0016、
ADR-0019決定1）。「もう一度探す」はこの切り口の数に数えない別の操作であるため、切り口の総数を増やす
将来の変更では、この関係が保たれるかを都度確認する必要がある（ADR-0016決定4・ADR-0019決定1が実際に
この確認を行った先例である）。予算感（`dinnerBudgetTier`）は切り口にせず、この4種の構成には数えない
——すべてのカードに常時示す参考情報である（後述）。

実データのフィールド調査（ADR-0019）を受け、`CAPACITY_REFERENCE`（総席数で並べ替える切り口）と
`AMENITY_REFERENCE`（個室・禁煙等を合算する切り口）は廃止した。総席数は切り口ではなく、すべての
カードに常時示す規模の目安（`capacityTier`: 少なめ／標準／多め）に変わった——この目安は店舗の規模だけを
表し、予約の取りやすさを意味しない。`AMENITY_REFERENCE`が合算していたフィールドのうち、禁煙区分
（`non_smoking`）だけが実データで充足率・分布とも良好だったため、単独の切り口`NON_SMOKING_REFERENCE`
として独立させた。新設した`GENRE_FOCUS`は、既定母集団の中で最多のジャンル1つに絞り込んで近い順に
並べる切り口であり、既定母集団に2種類以上のジャンルがある場合だけ提示する——この条件により、
`GENRE_FOCUS`の候補集合は提示される限り常に`PROXIMITY`の候補集合の真部分集合になり、`GENRE_VARIETY`
（ADR-0016で廃止）が実データで犯した「`PROXIMITY`と完全に同一の集合・順序を返す」という縮退を構造的に
再発させない。

カード払い可否（`card`）は切り口にも比較材料にもしない。利用不可のときだけ、カードに確認済みの事実
だけの注意（「クレジットカードは利用できません」）を出す——`card`はクレジットカード可否だけを追跡し、
電子マネー等の他の決済手段を含まないため、「現金のみ」とは断定しない（ADR-0019）。アクセス（生の住所
表記）は、地図が同じ情報を代替するため、カード・APIから完全に外した（ADR-0019）。

予算感（`dinnerBudgetTier`）も切り口にせず、すべてのカードに常時示す粗い3段階の参考情報とする
（少なめ／標準／多め相当）。この目安は必ず「ディナー」であることが分かる形で示し、ランチ価格を推論・
断定しない（ADR-0015が確立した「確認できないことを断定しない」原則の適用。ADR-0019決定8）。この
決定は当初のドラフトで一度全面却下されたが、却下理由の一部が循環していたことが判明し、人間の
再確認で採用へ差し戻された経緯を持つ（ADR-0019決定8）。

## 非公開データの扱い

| データ | 置き場 | 公開リポジトリに置かないもの |
|---|---|---|
| 検索基点・探索範囲 | runtime非公開設定 | 実在の地名、座標、距離、既定値 |
| API credential | server runtime secret | 値、キー入りURL、ログ、エラー、トレース |
| providerレスポンス | request中だけ | raw response、実店舗ID、店舗情報、画像、dump、実fixture |
| schema migration | Git | 実データを投入するdata migration、実fixture、DB dump |
| 利用済み・ブラックリスト | この製品では実装しない | provider ID、HMAC由来トークン、候補履歴、実店舗データの保存 |

Hot Pepper APIキーはprovider指定のクエリパラメータとしてserverから送る。adapterはURLをredactし、clientや観測可能な出力にキーを出さない。初期版はproviderレスポンスをcache・永続化しない。

この製品では長期照合を行わない。再提案時だけ、ブラウザが同じ画面で以前に表示した candidate の providerPageUrl をそのリクエストへ送り、サーバはその1リクエストの候補選定でだけ既表示候補を未表示候補より後ろへ置く（ADR-0017。ADR-0008決定2を置き換える）。これは新たにブラウザが収集した情報ではなく、サーバ自身が直前までに返した値をそのまま渡すものであり、サーバはそれを保存・ログ出力しない（ADR-0017決定3のMust要件）。ブラウザ側もこの一覧を同一画面のメモリだけに保持し、storage、cookie、URLへは書かず、更新・タブを閉じる・サインアウトで破棄する。この一覧の値は非公開の検索地点そのものではなく、既に同じ幹事の画面に表示済みの店舗ページURLである。利用済み・ブラックリスト（跨セッションでの継続的な照合・除外）を再検討する場合は、新たな人の意思決定、provider規約の再確認、新規ADRで判断する。

## provider境界

- Hot Pepperは唯一の初期providerであり、スクレイピングとfallbackは使わない。
- providerのcreditを表示する。provider画像は初期版で使わない。
- provider規約を、公開運用前、cache・画像・永続化を追加する前に再確認する。
- network、資格情報、rate limit、provider停止は外部境界の失敗として扱い、合成fixtureによるテストを基本とする。

## 後続スライスへの条件

- 実装前に、表示済み候補の二次順位低下（サーバが再提案リクエストごとに行う。ADR-0017）が候補履歴や
  provider-response cacheを作らないことを確認する。
- 実装時に、`previouslyShownProviderPageUrls`の値がログ・トレース・エラーレスポンスへ出力されないことを
  確認する（ADR-0017決定3のMust要件）。
- 実装時に、`test-support-api.yaml`の`NORMAL_WITH_REPEAT`合成候補を6件以上へ拡張し、既表示一覧が実際に
  選定へ効くことをL4で検証できるようにする（ADR-0017決定5）。
- 実装時に、必要なcreditの正確な表示文言・リンクを公式ガイドラインから確定する。
- providerが安全な通信経路をどう公開仕様化しているかを実装時に確認する。
- 実装時に、ランチ営業の実施が確認しづらいジャンルとして母集団から除外する対象を、公式のジャンル一覧（コードを含む）に照らして確定する。ジャンル文字列一致からジャンルコード一致へ切り替えるかどうかも、この確認と併せて判断する（ADR-0015）。
- 実装時に、`non_smoking`・`card`・`budget.average`の正確な生フィールド名と値の語彙を公式ドキュメントで
  確認する（`genre`について既に行っている確認と同じ扱い。ADR-0019決定9）。`capacityTier`のしきい値
  （20席以下／21〜60席／61席以上）、`dinnerBudgetTier`のしきい値（〜2,000円／2,001〜4,000円／
  4,001円〜、いずれもADR-0019決定4・8）は一回限りの実データ診断に基づく暫定値であり、より多くの実
  データが得られた時点で見直しの要否を確認する。
