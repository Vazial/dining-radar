# design.md — Dining Radar 設計骨子

> **承認者向けサマリ**: 非公開のruntime検索条件（検索基点・探索範囲）から店舗候補を絞り込んで示すDjangoモノリスの設計骨格である。外部provider連携と候補の適格性判定・絞り込み・順位付けを分離し、公開Gitにはschema migrationと合成fixtureだけを置く。この製品は実データの長期保存、利用履歴、ブラックリストを持たない。認証済み画面は検索基点と徒歩時間の目安を表示する（ADR-0025）。

## スコープ

このfoundationは、非公開のruntime検索条件で外部候補を探し、絞り込み・並べ替えた候補を示すための責務分割だけを定める。この製品は利用済み・ブラックリスト・跨セッションの候補履歴を実装しない。同じ条件のまま「もう一度探す」を選ぶと、近傍プールからの無作為抽出により候補集合が入れ替わりうる——ただしこれは確率的な多様性であり、既表示候補をサーバが決定的に照合・降格する仕組みではない（ADR-0023決定4・5。ADR-0008決定2・ADR-0017が定めていた再表示降格メカニズムを置き換えた）。画面、endpoint、DB schema、API接続、認証情報、実データは定めない。候補提案の現在の画面・APIの振る舞いは、ADR-0005・ADR-0023・ADR-0025とcandidate-search契約が定める。

候補提案は、管理者が作成した有効な個別幹事 account の same-origin Django session だけに開く。公開signup、
メールreset、SSOは初期スコープにない。認証・公開運用の状態と設定境界は ADR-0006、
`contracts/authentication.feature`、`contracts/authentication-api.md` が定める。ここでは認証画面、
管理画面、host、domain、email、session expiryの具体を定めない。

## 処理の流れ

```text
runtime検索条件（非公開の検索基点・探索範囲）
  -> Hot Pepper adapter（取得段階の切り捨て防止: results_availableがresults_returnedを
     上回る場合はページングで残りを取得する。ADR-0023決定3）
  -> provider形式を内部候補へ正規化・重複排除
  -> 既定では、ランチ営業の実施が確認しづらいジャンル（居酒屋・バー等）を候補母集団から除く。
     「居酒屋・バーを含める」絞り込みを選んだときだけ、そのジャンルも母集団に含める（ADR-0015）
  -> 幹事が選んだ絞り込み条件（ジャンル・禁煙・カード払い・予算感・徒歩の上限）を、取得・正規化した
     母集団全体に対して適用する（表示上限5件に対しては行わない。ADR-0023決定3）。いずれの条件も、
     確認できた非該当だけを除くソフトフィルタであり、情報なしの候補は除外せず後方へ回す
     （ADR-0023決定2）
  -> 並べ替えは常に「確認済み一致→情報なし、各段は検索基点からの近い順」の1種類だけであり、
     選択肢は設けない（ADR-0023決定1・4）
  -> 近い方から上位N件（非拘束の推奨値20。母集団がNを下回れば母集団全体）を抽出プールとし、
     そこから表示件数（最大5件）を無作為抽出する。抽出後、表示直前に同じ2段の順序へ並べ直す
     （ADR-0023決定4）
  -> 候補の提示（必要なcreditを併記）。「もう一度探す」は適用済みの条件のまま同じ抽出をやり直す
     だけの操作であり、独自の順位付け基準を持たない（ADR-0023決定4・5）
```

候補の複数人利用可否や予約可否は、providerが返す参考情報であり保証しない。providerの店舗事実は変更せず、アプリ側は選択・除外・順序付けのみを行う。総席数の目安（`capacityTier`）、予算感の目安（`dinnerBudgetTier`）、カード払いに関する注意（`cardPaymentAvailable`が`false`の時だけ表示）、徒歩時間の目安（`walkingTimeMinutes`、分単位の整数。推定であり実測経路ではないと分かる形で示す。ADR-0025）はいずれもカードの表示専用の派生値であり、並べ替え自体には関与しない——並べ替えは常に検索基点からの距離昇順である。

## 検索基点・徒歩時間の開示

認証済み画面は、検索基点をマーカーとして地図に示し、そこを中心とする徒歩圏の同心リングを描く。候補カードには徒歩時間の目安を表示する。徒歩の上限（`walkingTimeMaxMinutes`）は、ジャンル・禁煙・カード払い・予算感と同格の絞り込み条件の一つとして扱う（ADR-0025決定1〜3）。

これは`ADR-0004`・`ADR-0008`決定4が課していた「検索基点・徒歩時間をbrowserへ一切開示しない」というMustのうち、**browserへの非開示だけを撤回した結果**である。次は無変更のまま維持する（ADR-0025決定4〜6）。

- 検索基点の実座標・設定探索範囲の値は、引き続き環境変数などのruntime非公開設定に置き、Gitには一切置かない。
- 公開URL・ログ・エラー・traceへの非開示も維持する。
- 徒歩**経路**と現在地は表示しない。前者は外部の経路探索通信を要し、後者は利用者本人の実時間の居場所であり検索基点とは別種の情報である。
- タイル提供者へ検索基点を渡さないため、`Referrer-Policy: strict-origin-when-cross-origin`を維持する。

設定探索範囲そのものの値は、API応答・DOM・公開URL・ログ・traceのどこにも出さない。同心リングの本数・半径の選び方によって設定探索範囲が間接的に推測されうることは許容する——許容するのは推測可能性であって値そのものの露出ではない（ADR-0025決定9、人間裁定2026-08-20）。

## 候補提案の画面投影

```text
サインイン済みの幹事が候補提案画面を開く
  -> 既定条件（絞り込みなし。居酒屋・バー等の既定除外だけが効く）による候補カード（最大5件）と、
     検索基点マーカー・徒歩圏の同心リング・候補店舗マーカーを示す地図を表示する
  -> カードとマーカーを相互に強調して比較する

（条件を変える経路）
サインイン済みの幹事が絞り込みパネルを開き、条件（ジャンル・居酒屋バーを含めるか・禁煙・カード払い・
予算感・徒歩の上限）を変える
  -> 変更は「保留中」の条件としてだけ記録され、適用するまで表示中の候補・地図・条件要約・適用済みの
     条件は変わらず、検索も行わない（ADR-0023決定8）
  -> 適用すると、保留中の条件で新しい候補提案を依頼し、カード・地図全体を置き換える
  -> 取り消すと、保留中の条件を適用済みの条件へ戻すだけで、パネルは開いたままとし、検索は行わない

（別経路）
サインイン済みの幹事が「もう一度探す」を選ぶ（ADR-0023決定4）
  -> 適用済みの条件のまま新しい候補提案を依頼する
  -> 新しい候補提案でカード・地図全体を置き換える
  -> 新しい候補が以前とすべて異なる店舗になるとは限らない
```

初期表示では絞り込みなし（居酒屋・バー等の既定除外だけが効く）で候補を示す。補助条件は絞り込みパネルを開くまで見えない。手動ソート・自由入力の検索条件は設けない——並べ替えは常に近い順の1種類だけである（ADR-0023決定1）。詳細な受け入れ状態とbrowser-facing APIは `contracts/candidate-search.feature` と `contracts/candidate-search-api.yaml` を参照する。

「もう一度探す」は、条件を変える操作とは異なる。適用済みの条件をそのまま使って新しい候補提案を依頼するだけの操作であり、絞り込み条件も並べ替え規則も変えない。新しい候補が現れるかどうかは、近い方から上位N件の抽出プールからの無作為抽出に依存する（ADR-0023決定4）。ADR-0008・ADR-0017が定めていた、既表示候補をサーバが二次的に順位低下させる仕組みは廃止した——無作為抽出そのものが表示の多様性を担い、既表示履歴の送受信・保存は一切行わない（ADR-0023決定5）。

各絞り込みの候補は最大5件まで表示する（ADR-0015）。絞り込み・並べ替えは取得・正規化した母集団全体に対して行い、5件は表示段階だけに適用する表示上限であって、取得・順位付け対象の上限ではない（ADR-0023決定3）。ランチ営業の実施が確認しづらいジャンル（居酒屋・バー等）は既定の母集団から除き、幹事が「居酒屋・バーを含める」絞り込みを選んだときだけ母集団に含める。この除外は「確認できないランチ営業実態を確定的な事実として断定しない」という判断である。除外の結果すべての絞り込みで候補が0件になる場合は、この既定除外だけを緩めて再計算する——幹事が明示的に選んだ他の絞り込み条件は緩めない（ADR-0023決定6）。

絞り込み条件はジャンル・居酒屋バーを含めるか・禁煙・カード払い・予算感・徒歩の上限の6項目であり（ADR-0015、ADR-0023、ADR-0025決定3）、いずれもソフトフィルタである——条件に対して「確認できた非該当」だけを除き、情報がない候補は除外せず、表示順では確認済み一致の候補群より後ろに置く（ADR-0023決定2）。

総席数は比較の並べ替え基準にせず、すべてのカードに常時示す規模の目安（`capacityTier`: 少なめ／標準／多め）とする——この目安は店舗の規模だけを表し、予約の取りやすさを意味しない（ADR-0019）。

カード払い可否（`card`）は絞り込み条件の一つであり、比較材料や並べ替え基準にはしない。利用不可のときだけ、カードに確認済みの事実だけの注意（「クレジットカードは利用できません」）を出す——`card`はクレジットカード可否だけを追跡し、電子マネー等の他の決済手段を含まないため、「現金のみ」とは断定しない（ADR-0019）。アクセス（生の住所表記）は、地図が同じ情報を代替するため、カード・APIから完全に外した（ADR-0019）。

予算感（`dinnerBudgetTier`）は絞り込み条件の一つであると同時に、すべてのカードに常時示す粗い3段階の参考情報である。段階語（低・中・高）だけを示し、円のレンジは示さない。「ディナー予算をもとにした目安であり、ランチ価格を示すものではない」という開示は、カードごとに繰り返さず、展開中の絞り込みパネル内に1行だけ置く（ADR-0023決定7・10、ADR-0019決定8を部分置換）。

## 非公開データの扱い

| データ | 置き場 | 公開リポジトリに置かないもの |
|---|---|---|
| 検索基点・探索範囲 | runtime非公開設定。検索基点は認証済み画面にマーカーとして表示する（ADR-0025） | 実在の地名、座標そのものの値、既定探索距離の値 |
| API credential | server runtime secret | 値、キー入りURL、ログ、エラー、トレース |
| providerレスポンス | request中だけ | raw response、実店舗ID、店舗情報、画像、dump、実fixture |
| schema migration | Git | 実データを投入するdata migration、実fixture、DB dump |
| 利用済み・ブラックリスト・候補履歴 | この製品では実装しない | provider ID、HMAC由来トークン、候補履歴、実店舗データの保存 |

Hot Pepper APIキーはprovider指定のクエリパラメータとしてserverから送る。adapterはURLをredactし、clientや観測可能な出力にキーを出さない。初期版はproviderレスポンスをcache・永続化しない。

この製品は長期照合・跨セッションの候補履歴を持たない。「もう一度探す」で候補集合が入れ替わりうるのは近傍プールからの無作為抽出によるものであり、サーバは既表示候補の一覧を送受信・保存しない（ADR-0023決定5）。利用済み・ブラックリスト（跨セッションでの継続的な照合・除外）を再検討する場合は、新たな人の意思決定、provider規約の再確認、新規ADRで判断する。

## provider境界

- Hot Pepperは唯一の初期providerであり、スクレイピングとfallbackは使わない。
- providerのcreditを表示する。provider画像は初期版で使わない。
- provider規約を、公開運用前、cache・画像・永続化を追加する前に再確認する。
- 絞り込みはローカルの正規化済み母集団に対して行う。ジャンルはprovider側パラメータへ渡すことも技術的には可能だが、ジャンルコード解決が未了のため当面は据え置く（ADR-0015）。予算・禁煙・カード払いは、provider側パラメータの制約（予算は最大2コード、禁煙・カード払いは情報なしの候補も除いてしまう単純な真偽フィルタ）がソフトフィルタの方針と両立しないため、provider側パラメータとしては使わない（ADR-0023決定3）。
- network、資格情報、rate limit、provider停止は外部境界の失敗として扱い、合成fixtureによるテストを基本とする。

## 後続スライスへの条件

- 実装時に、必要なcreditの正確な表示文言・リンクを公式ガイドラインから確定する。
- providerが安全な通信経路をどう公開仕様化しているかを実装時に確認する。
- 実装時に、ランチ営業の実施が確認しづらいジャンルとして母集団から除外する対象を、公式のジャンル一覧（コードを含む）に照らして確定する。ジャンル文字列一致からジャンルコード一致へ切り替えるかどうかも、この確認と併せて判断する（ADR-0015）。
- 実装時に、`non_smoking`・`card`・`budget.average`の正確な生フィールド名と値の語彙を公式ドキュメントで
  確認する（`genre`について既に行っている確認と同じ扱い。ADR-0019決定9）。`capacityTier`のしきい値
  （20席以下／21〜60席／61席以上）、`dinnerBudgetTier`のしきい値（〜2,000円／2,001〜4,000円／
  4,001円〜、いずれもADR-0019決定4・8）は一回限りの実データ診断に基づく暫定値であり、より多くの実
  データが得られた時点で見直しの要否を確認する。
- 実装時に、徒歩時間の算出にメートル換算が必要であることを確認する——`recommendation/pipeline.py`の
  `_distance()`は度単位を返しており、これはADR-0025以前は正確な距離をブラウザへ返さない前提のもと
  問題にならなかった（docstringに理由が明記されている）。ADR-0025でこの前提が崩れたため、徒歩時間の
  表示にはメートル換算が要る。
- 徒歩時間の算出方式（直線距離か道のり基準か）はADR-0025決定2が実装スライスへ送った判断である——
  直線距離からの概算を採ることは人間の選択で既に決着している。
- `src/dining_radar/**`はmutation testingの対象であり、上記の変更にはテストが要る。
