## 目的

幹事が3〜5件のランチ候補を横並びで見比べて1件に絞り込むための「候補カード」を、情報階層と可読性の
観点から設計する。画面全体の骨格（後述）は既に人間承認済みであり保つ。**設計の焦点はカード1枚の
中身と、カードが並んだときの読み取りやすさである。**

## 対象ユースケース

月1回程度、5人前後のランチ会の幹事が、サインイン直後に表示された候補を見比べる。幹事がカードから
判断したいのは次の4点で、それ以上ではない。

1. これはどんな店か（料理の種類・雰囲気の手がかり）
2. その時間帯に開いていそうか（営業時間・定休日）
3. 人数的に無理がなさそうか（総席数。あくまで参考値で、席の確保を意味しない）
4. どのあたりにあるか（アクセスの説明と、地図上のどのマーカーか）

判断がついたら、店舗の外部ページへ移動してメニュー・営業状況・予約可否を最終確認する。カードは
決定を下す場所ではなく、**候補を絞り込み、外部確認へ送り出す場所**である。

ログイン画面、アカウント管理、デプロイの画面は設計しない。

## ★ round 1 が却下された理由（同じ失敗を繰り返さないために）

この製品は**公開リポジトリで開発されており、非公開の検索地点を秘匿することが製品要件そのもの**である。
そのため、設計成果物に置けるデータには絶対の制約がある。round 1 は次に違反した。

1. **緯度経度の数値をデータに置いた**（`location: { latitude: 35.6812, longitude: 139.7671 }`）。
   描画には一切使っていなかったにもかかわらず、fixture にだけ残っていた。
2. **実在の地名を置いた**（地図パネルに「◯◯市中心部」という注記）。しかも上記の座標は別の都市を
   指しており、辻褄も合っていなかった。
3. **架空と分からない店舗名を作った**（1件を除き、実在店舗と衝突しないと判別できない名前だった）。
4. **取得できない事実を断定した**。例:「今回は5名でのご利用とのことですので」（人数を入力する画面は
   存在しない）、「スムーズに入りやすい可能性のある店舗」（混雑は取得できない）、「移動時間を最小限に」
   （徒歩時間は取得も表示もしない）、「静かめで落ち着いた会話がしやすい空間」（設備情報から導けない）。
5. **安全でないエラーコピーを書いた**。例:「開発者コンソールもしくはシステム構成を確認してください」
   「管理者によって権限設定が変更された可能性があります」「サーバー負荷保護のため」「十分な空席…が
   本日見つかりませんでした」「幹事の嗜好と…を計算しています」。この製品は権限モデルも嗜好の保存も
   特定日の営業判定も持たず、内部事情を利用者に見せてはならない。
6. **エラーコードと HTTP ステータスを画面に表示した**（`PROVIDER_UNAVAILABLE (503)` 等）。利用者向けの
   安全な文だけを見せる。コードはコメントに書く。
7. **再提案後も、現在表示中の切り口が選択肢に残っていた**。

**この失敗を根本から絶つため、round 2 では表示データと文言を下記のとおり指定する。**
**あなたが作るのは情報階層と視覚構成であり、データと文言ではない。**

## ドメインルール（最小限）

### カードに載る情報（これで全部。増やせない）

店名／ジャンル／紹介文／営業時間／定休日／総席数／アクセス／店舗詳細ページへのリンク。

- **紹介文・営業時間・定休日・総席数・アクセスは `null` になりうる**（上の表に実例がある）。
  欠損時は中立な欠損表示（例:「情報なし」）にする。**欠損の多いカードが、情報の揃ったカードに比べて
  壊れて見えたり、不当に見劣りしたりしない**ことが要件である。
- **各項目はそれぞれラベルを持ち、個別に識別できる必要がある**（受け入れ検証がラベルと値の対応を
  観測するため）。ラベルの文言・見せ方（常時表示・アイコン併記・グループ化・読み上げ専用）は自由。
- 総席数は provider の参考値であり、空席・予約可否・グループ利用の可否を保証しない。
  可視表示に単位を付けてよい（`38席`）。
- 存在しないもの: 価格帯、支払方法、空席、予約可否、徒歩時間、距離、現在地、経路、評価スコア、写真。
  これらを匂わせるバッジ・指標・比較軸を発明しない。

### カードの並びと状態

- 並び順はサーバーが決める。**幹事は並び替えられない**（手動ソート・フィルタ・ページングを置かない）。
- 1つの提案の候補は3〜4件。「もっと見る」で追加しない。
- カードと地図マーカーは**相互に強調する**。カードを選ぶと対応するマーカーが、マーカーを選ぶと対応する
  カードが強調される。番号などの対応付けの手がかりが要る。
- **再提案の後、同じ画面で既に表示した店舗は、まだ表示していない店舗より後ろに置かれる。ただし
  除外はされない。** 4件しかない合成データを提案ごとに組み替えれば、この状態は自然に作れる。
  カードが「初出」「再登場」のどちらかであることを可視化するかどうか、するならどう見せるかは
  設計判断に委ねる。
- 内部識別子（`candidateRef` / `conceptRef`）は画面に出さない。

### 画面全体（人間承認済み。保つ）

サインイン済みの幹事が画面を開くと、**条件入力もコンセプト選択も求めずに**、1つの切り口による候補と
地図が直ちに表示される。合わないときだけ「別の切り口で再提案」を押すと、**現在表示中の切り口を除く**
最大3つの切り口がモーダルで示され、1つ選ぶと**新しい提案でカードと地図の全体が置き換わる**（追加ではない）。
**再提案した後は、その時点で表示中の切り口が選択肢から外れていなければならない**（round 1 の不備）。

保つべき主要ブロックの存在は次のとおり。**この中でのカードの内部設計・密度・幅の取り方・一覧の
並べ方・地図とカードの面積配分は自由に設計してよい。**

- ヘッダー
- 現在の切り口の見出し（タイトルと根拠）＋「別の切り口で再提案」の起点
- 候補の地図（合成表現）と、候補カード一覧（この2つを見比べる関係）
- 再提案モーダル（最大3つの切り口）
- provider credit を含むフッター
- レビュー状態の切替コンソール（**プロダクトUIと視覚的・意味的に分離する**。プロダクト画面の中に
  レビュー用の操作を混ぜない。round 1 は未認証画面に「ダミーサインイン」ボタンを埋め込んでいた）

### 表示義務

- Hot Pepper credit は正確な文言 `Powered by ホットペッパーグルメ Webサービス` を
  `http://webservice.recruit.co.jp/` へのリンクとして示す。
- 地図には `© OpenStreetMap contributors` の帰属表示を示し、
  `https://www.openstreetmap.org/copyright` へリンクする。
- 検索地点は非公開である。地点名・座標・距離・基点マーカー・経路・現在地・徒歩時間を、入力にも表示にも
  出さない。地図に出るのは候補店舗だけである。**「検索地点は非公開です」といった注記を置くのは構わないが、
  その地点が何であるか（住所・施設の種類など）に言及しない。**

### 置いてはならない操作

候補提案画面に置ける操作は、**カードの選択／マーカーの選択／再提案を開く・選ぶ・送る・取り消す**、
およびサインアウト・パスワード変更だけである。絞り込み、並べ替え、範囲・ジャンルの指定、
**「再試行」ボタン**（round 1 が候補なし状態に置いた）は、契約上その画面に存在できない。

## 現在のバックエンドAPI（列挙）

### `POST /candidate-proposals`

認証済み same-origin セッション前提。初回表示は空リクエスト、再提案は `reproposalKind`（現在の
`reProposalOptions` から選んだ1つ）のみを送る。

成功応答（200）:

- `proposal`: 候補なしのとき `null`。あるときは `conceptRef` / `kind`（`PROXIMITY` /
  `CAPACITY_REFERENCE` / `GENRE_VARIETY` / `AMENITY_REFERENCE`）/ `title` / `rationale` / `candidates[]`
- `reProposalOptions[]`: 最大3件。各要素は `kind` / `title` / `rationale` のみ
- `providerCredit`: `{ text, url }`（固定文言・固定URL）

`Candidate` が持つのは次だけである。**カードに出せるのはこれで全部**である。

- `candidateRef`（画面に出さない内部識別子）
- `name` / `genre`
- `description` / `businessHours` / `regularHoliday` / `access`（いずれも `string | null`）
- `totalSeats`（`integer | null`）
- `providerPageUrl`
- （本番のみ）候補店舗の位置。**設計成果物では座標を持たず、レビュー用のレイアウト値で代用する**

問題応答: `400 PROPOSAL_REPROPOSAL_KIND_INVALID` / `401 AUTHENTICATION_REQUIRED` /
`403 REQUEST_REJECTED` / `429 PROPOSAL_RATE_LIMITED` / `503 PROVIDER_UNAVAILABLE`。
**画面には安全な文だけを見せ、コードは TSX のコメントに書く。**

**上記のAPIに無い情報が理想の情報階層に必要だと判断した場合は、存在を仮定せず、成果物内の
`Required API additions` block comment に列挙してよい。** 追加が不要なら
`Required API additions: None required.` と正確に記す。

## 解決したい問題

人間からの具体的な不満点はまだ示されていない。以下は契約と現在の画面から導ける緊張点であり、
**解き方も、そもそもこれらが問題かの判断も、設計側に委ねる**。

1. **8項目が均等な重みで並ぶと、比較の軸が立たない。** 幹事が実際に見比べているのは「どんな店か」
   「開いていそうか」「人数的に無理がなさそうか」「どこか」の4点であり、8項目はそのための材料である。
   材料をそのまま等価に並べることと、判断の軸に沿って階層化することは別のことである。
2. **カードの横幅は地図と分け合う。** 密度と可読性を同時に立てる必要がある。
3. **欠損が普通に起きる。** 5項目のうち任意の組み合わせが `null` になりうる。欠損の穴がレイアウトを
   崩さず、かつ「情報なし」が並んだカードが読み捨てられない扱いが要る。
4. **参考値が保証に見えてはならない。** 総席数は最も誤読されやすい項目である。
5. **再提案後の「初出／再登場」の区別が現在は見えない。** 契約上は順序で表現されているだけで、幹事は
   なぜその並びなのかを知る手がかりを持たない。
6. **現状のカード**（置き換え対象）は、店名＋ジャンルチップ＋紹介文の下に、営業時間／定休日／総席数／
   アクセスを**アイコン付きラベルの2×2グリッド**で並べ、最後に外部リンクを置く形である。
   これが唯一の解であるとは限らない。**この構造を保つ必要はない。**

## 制約からの解放

既存のカード構造・既存のCSS・既存のクラス名に縛られず、幹事にとって最も読みやすく比較しやすい
カードを設計してよい。上の主要ブロックの存在だけが保つべき境界であり、その内側は自由である。
**却下されたのは境界違反と文言であって、視覚設計ではない。** 与えたデータとコピーを器に、
**カード1枚の情報階層と、それが並んだときの一覧の読み取りやすさ**に出力を集中してほしい。

## 技術前提

成果物は隔離されたレビュー専用 receiver `projects/dining-radar/design-preview/` だけで描画する。
Django本体・provider・実APIには接続しない。

**receiver の実際の構成（重要）**:

- React 19 + TypeScript + Vite。エントリが `src/screens/CandidateSearchPreview.tsx` の default export を
  1つ描画するだけである。
- 利用できる依存は `react` / `react-dom` / `lucide-react` **のみ**。**Tailwind も shadcn/ui も
  インストールされていない。** Tailwind のユーティリティクラスを書いても一切スタイルが当たらない。
- グローバルCSS が読み込まれたままだが、**前世代の画面のクラス名に密結合したプレーンCSS**である。
  既存クラス名に寄せると前世代のレイアウトに引きずられる。
- したがって成果物は**視覚的に自己完結していること**。コンポーネント内に `<style>{`...`}</style>` を
  持たせて自前のCSSを同梱するか、インライン style で完結させる。クラス名は衝突を避けるため独自の
