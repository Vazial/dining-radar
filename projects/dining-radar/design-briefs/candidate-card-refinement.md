# Design brief — 候補カードの情報階層と可読性

> Status: draft brief for external design commissioning (designer (a), meta/adr/0018・0020・0021).
> 対象契約は承認済みで実装も完了している（`candidate-search.feature` / `candidate-search-api.yaml` v0.4.0 /
> `candidate-search-browser-interface.yaml` v0.2）。本ブリーフは画面骨格の再設計を求めるものではなく、
> **候補カードの内部設計に出力を集中させる**ための発注書である。可視コピーはすべてドラフトであり、
> 最終確定ではない。合成・非機微データのみを使う。

## 目的

幹事が3〜5件のランチ候補を横並びで見比べて1件に絞り込むための「候補カード」を、情報階層と可読性の
観点から設計し直す。画面全体の骨格（後述）は承認済みであり保つ。**設計の焦点はカード1枚の中身と、
カードが並んだときの読み取りやすさである。**

## 対象ユースケース

月1回程度、5人前後のランチ会の幹事が、サインイン直後に表示された候補を見比べる。幹事がカードから
判断したいのは次の4点で、それ以上ではない。

1. これはどんな店か（料理の種類・雰囲気の手がかり）
2. その時間帯に開いていそうか（営業時間・定休日）
3. 5人で行って無理がなさそうか（総席数。あくまで参考値で、席の確保を意味しない）
4. どのあたりにあるか（アクセスの説明と、地図上のどのマーカーか）

判断がついたら、店舗の外部ページへ移動してメニュー・営業状況・予約可否を最終確認する。カードは
決定を下す場所ではなく、**候補を絞り込み、外部確認へ送り出す場所**である。

ログイン画面、アカウント管理、デプロイの画面は設計しない。

## ドメインルール（最小限）

### カードに載る情報（これで全部。増やせない）

| 項目 | 性質 |
|---|---|
| 店名 | 常にある |
| ジャンル | 常にある。provider の語をそのまま出し、言い換えない |
| 紹介文 | 無いことがある |
| 営業時間 | 無いことがある。文字列（例: `11:00〜14:30`）。曜日別・当日判定はしない |
| 定休日 | 無いことがある。文字列（例: `日曜・祝日`） |
| 総席数 | 無いことがある。整数。可視表示に単位を付けてよい（`38席`） |
| アクセス | 無いことがある。文字列の説明のみ。距離・徒歩分数は存在しない |
| 店舗詳細ページへのリンク | 常にある。外部確認の唯一の出口 |

- 欠損時は中立な欠損表示（例:「情報なし」）にする。**欠損の多いカードが、情報の揃ったカードに比べて
  壊れて見えたり、不当に見劣りしたりしない**ことが要件である。
- 総席数は provider の参考値であり、**空席・予約可否・グループ利用の可否を保証しない**。保証や推測に
  読める表現（「◯人までOK」「ゆったり座れる」等）を作らない。
- 存在しないもの: 価格帯、支払方法、空席、予約可否、徒歩時間、距離、現在地、経路、評価スコア、写真。
  これらを匂わせるバッジ・指標・比較軸を発明しない。
- 各項目はそれぞれ独立したラベルを持ち、個別に識別できる必要がある（受け入れ検証がラベルと値の
  対応を観測するため）。ラベルの文言・見せ方（常時表示・アイコン併記・グループ化）は自由だが、
  **項目を1行に統合してしまう案を採りたい場合は、その旨を成果物のコメントで指摘すること**（契約の
  改訂点として別途扱う）。

### カードの並びと状態

- 並び順はサーバーが決める。**幹事は並び替えられない**（手動ソート・フィルタ・ページングを置かない）。
- 1つの提案の候補は3〜5件程度。「もっと見る」で追加しない。
- カードと地図マーカーは**相互に強調する**。カードを選ぶと対応するマーカーが、マーカーを選ぶと対応する
  カードが強調される。番号などの対応付けの手がかりが要る。
- 再提案（後述）の後、**同じ画面で既に表示した店舗は、まだ表示していない店舗より後ろに置かれる。
  ただし除外はされない**。カードは「初出」「再登場」のどちらかの状態を持つ。現在の画面はこの区別を
  可視化していない。**可視化するかどうか、するならどう見せるかは設計判断に委ねる。**
- 内部識別子（`candidateRef` / `conceptRef`）は画面に出さない。

### 画面全体（承認済み。保つ）

サインイン済みの幹事が画面を開くと、**条件入力もコンセプト選択も求めずに**、1つの切り口による候補と
地図が直ちに表示される。合わないときだけ「別の切り口で再提案」を押すと、現在の切り口を除く最大3つの
切り口がモーダルで示され、1つ選ぶと**新しい提案でカードと地図の全体が置き換わる**（追加ではない）。

保つべき主要ブロックの存在と配置は次のとおり。この骨格の中でのカードの内部設計・密度・幅の取り方・
一覧の並べ方は自由に設計してよい。

- ヘッダー
- 現在の切り口の見出し（タイトルと理由）＋「別の切り口で再提案」の起点
- 候補の地図（合成表現）と、候補カード一覧（この2つを見比べる関係）
- 再提案モーダル（最大3つの切り口）
- provider credit を含むフッター
- レビュー状態の切替コンソール（プロダクトUIと視覚的に分離する）

### 表示義務

- Hot Pepper credit は正確な文言 `Powered by ホットペッパーグルメ Webサービス` を
  `http://webservice.recruit.co.jp/` へのリンクとして示す。
- 地図には OpenStreetMap の帰属表示を示す。
- 検索地点は非公開である。地点名・座標・距離・基点マーカー・経路・現在地・徒歩時間を、入力にも表示にも
  出さない。地図に出るのは候補店舗だけである。

## 現在のバックエンドAPI（列挙）

### `POST /candidate-proposals`

認証済み same-origin セッション前提。初回表示は空リクエスト、再提案は `reproposalKind`（現在の
`reProposalOptions` から選んだ1つ）のみを送る。

成功応答（200）:

- `proposal`: 候補なしのとき `null`。あるときは `conceptRef` / `kind`（`PROXIMITY` /
  `CAPACITY_REFERENCE` / `GENRE_VARIETY` / `AMENITY_REFERENCE`）/ `title` / `rationale` / `candidates[]`
- `reProposalOptions[]`: 最大3件。各要素は `kind` / `title` / `rationale` のみ
- `providerCredit`: `{ text, url }`（固定文言・固定URL）

`Candidate` が持つのは次のフィールドだけである。**カードに出せるのはこれで全部**である。

- `candidateRef`（画面に出さない内部識別子）
- `name` / `genre`
- `description` / `businessHours` / `regularHoliday` / `access`（いずれも `string | null`）
- `totalSeats`（`integer | null`）
- `location`（`{ latitude, longitude }`。本番の地図マーカー描画専用）
- `providerPageUrl`

問題応答: `400 PROPOSAL_REPROPOSAL_KIND_INVALID` / `401 AUTHENTICATION_REQUIRED` /
`403 REQUEST_REJECTED` / `429 PROPOSAL_RATE_LIMITED` / `503 PROVIDER_UNAVAILABLE`。画面には応答の安全な
`message` だけを使い、内部事情を補足しない。

**上記のAPIに無い情報が、理想の情報階層に必要だと判断した場合は、存在を仮定せず、成果物内の
`Required API additions` block comment に列挙してよい。** 追加が不要なら
`Required API additions: None required.` と正確に記す。この指摘は突き合わせ工程の入口として扱われる。

## 解決したい問題

**正直な断り**: 人間からは「アプリが実装されたら候補カードの情報階層と可読性を検討する」という保留の
解除だけが示されており、**具体的な不満点はまだ示されていない**。以下は契約と現在の画面から導ける
緊張点であり、人間の批評ではない。したがって、ここに挙げた点の解き方も、**そもそもこれらが問題かの
判断も、設計側に委ねる**。

1. **8項目が均等な重みで並ぶと、比較の軸が立たない。** 幹事が実際に見比べているのは「どんな店か」
   「開いていそうか」「人数的に無理がなさそうか」「どこか」の4点であり、8項目はそのための材料である。
   材料をそのまま等価に並べることと、判断の軸に沿って階層化することは別のことである。
2. **カードの横幅は地図と分け合う。** 一覧は狭い領域に3〜5件が入る。密度と可読性を同時に立てる必要が
   ある。
3. **欠損が普通に起きる。** 5項目のうち任意の組み合わせが `null` になりうる。欠損の穴がレイアウトを
   崩さず、かつ「情報なし」が並んだカードが読み捨てられない扱いが要る。
4. **参考値が保証に見えてはならない。** 総席数は最も誤読されやすい項目である。
5. **再提案後の「初出／再登場」の区別が現在は見えない。** 契約上は順序で表現されているだけで、幹事は
   なぜその並びなのかを知る手がかりを持たない。
6. **現状の実装**（置き換え対象）は、店名＋ジャンルチップ＋紹介文の下に、営業時間／定休日／総席数／
   アクセスを**アイコン付きラベルの2×2グリッド**で並べ、最後に外部リンクを置く形である。これが唯一の
   解であるとは限らない。**この構造を保つ必要はない。**

## 制約からの解放

既存のカード構造・既存のCSS・既存のクラス名に縛られず、幹事にとって最も読みやすく、比較しやすい
カードを設計してよい。上に挙げた画面骨格（主要ブロックの存在と配置）だけが保つべき境界であり、
その内側は自由である。契約に無い情報が必要なら、勝手に仮定せず `Required API additions` に書く。
API細部や将来機能の網羅より、**カード1枚の情報階層と、それが並んだときの一覧の読み取りやすさ**に
出力を集中してほしい。

## 技術前提

成果物は隔離されたレビュー専用 receiver `projects/toyama-dining-radar/design-preview/` だけで描画する。
Django本体・provider・実APIには接続しない。

**receiver の実際の構成（重要）**:

- React 19 + TypeScript + Vite。エントリは `src/main.tsx` が `src/screens/CandidateSearchPreview.tsx` の
  default export を1つ描画するだけである。
- 利用できる依存は `react` / `react-dom` / `lucide-react` のみである。**Tailwind も shadcn/ui も
  インストールされていない**。Tailwind のユーティリティクラスを書いても一切スタイルが当たらない。
- グローバルCSS `src/styles.css` は**前世代の画面のクラス名に密結合したプレーンCSS**である。新しい
  クラス名を書いてもスタイルは付かず、既存クラス名に寄せると前世代のレイアウトに引きずられる。
- したがって成果物は**視覚的に自己完結していること**。コンポーネント内に `<style>{`...`}</style>` を
  持たせて自前のCSSを同梱するか、インライン style で完結させる。`styles.css` の既存クラス名に依存
  しない。クラス名は衝突を避けるため独自の接頭辞を付ける（グローバルCSSは読み込まれたままである）。
  ルート要素は自前で背景・タイポグラフィを指定し、外側の指定に依存しない。
- アイコンが要るなら `lucide-react` を使う。画像アセットは追加できない。

**データと通信の境界**:

- network request、fetch、実API、実Leaflet/OpenStreetMapタイル取得、位置情報、local storage、
  永続化を一切持たない。画面内の合成データとレビュー用の一時状態だけを持つ。
- 実店舗、実地名、実座標、数値距離、provider レスポンス・ID・画像、資格情報、キー入りURLを含めない。
- 店舗名・ジャンル・紹介文は、**架空だと一目で分かる**日本語のサンプルにする（例: `架空食堂 青い匙`）。
- アクセスの文字列に**距離や徒歩分数を書かない**（例:「駅より徒歩3分」は禁止。合成データであっても
  リポジトリに置けない）。「架空オフィス街の南側」のような非計量の説明にする。
- 店舗詳細リンクは `https://example.invalid/` 配下の不活性な合成URLにする。
- 地図は実タイルを取得しない合成表現とする。マーカー配置は座標ではなくレビュー用のレイアウト値
  （%位置など）で表し、本番では `Candidate.location` に対応することをソースコメントで注記する。
  このレイアウト値はAPIフィールドでもAPI追加要求でもない。
- provider credit の契約済みURLと OpenStreetMap の帰属リンクを除き、外部サービスへの通信を発生させない。

## 成果物の指定

`projects/toyama-dining-radar/design-preview/src/screens/CandidateSearchPreview.tsx` を**完全に置き換える
raw な TSX ソース1ファイルだけ**を返す。Markdown のコードフェンス、前置きの説明文、実装計画、
package ファイル、receiver の足場、Django コード、自己完結HTMLを返さない。成果物は**無改変でそのまま
配置し描画できなければならない**。

成果物に含めるもの:

1. **候補カードの設計（ここに出力を集中する）**: 8項目すべてを確認でき、`null` の中立表示の実例を
   少なくとも1件含み、カードが3〜5件並んだ状態で比較の読み取りやすさを確認できること。
2. 承認済み骨格の動作: 初回操作なしの提案表示、地図とカードの相互強調、最大3つの切り口を示す再提案
   モーダル、選択後の全体置換。補助条件・常設コンセプト一覧・手動ソート・ページングは置かない。
3. 再提案後に「初出」と「再登場」が混ざった状態を、レビューで確認できるようにする（可視化の有無と
   方法は設計判断。順序の規則自体は契約が定めるとおり、初出が先・再登場が後）。
4. 正確な linked provider credit と、見える OpenStreetMap 帰属表示。
5. プロダクトUIと視覚的・意味的に分離したレビュー状態切替。切り替えられる状態:
   `TDR-CS-00`（未認証。候補・地図・再提案の入口を一切見せない）、`TDR-CS-01`（通常の初期提案）、
   `TDR-CS-02`（カードと地図の相互強調）、`TDR-CS-03`（再提案モーダル・再提案中・置換後）、
   `TDR-CS-05`（候補なし）、`TDR-CS-06`（`503 PROVIDER_UNAVAILABLE`）、
   `TDR-CS-07`（`400 PROPOSAL_REPROPOSAL_KIND_INVALID`）、`TDR-CS-08`（`429 PROPOSAL_RATE_LIMITED`。
   待機の案内を安全に示す）、初回ロード中、`403 REQUEST_REJECTED`。
6. ソースコメントで、主要な可視要素・状態を、対応する `TDR-CS` シナリオID・APIフィールド・problem
   code に注記する。`candidateRef` / `conceptRef` はソース内の現応答限りの identity としてのみ使い、
   画面に表示しない。
7. 独立した `Required API additions` block comment（不要なら `None required.` と正確に記す）。

コピー（ラベル・空状態・エラー文言）はすべてドラフトとして書いてよい。最終確定ではない。
