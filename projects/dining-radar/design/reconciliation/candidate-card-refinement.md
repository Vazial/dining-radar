# 第1部 — 実装引き継ぎ

## 0. 前提: 何が「タタキ」で、何が既に緑なのか

この切り分けを誤ると、直す必要のないものを直すことになる。

- **タタキ**: `design-preview/src/screens/CandidateSearchPreview.tsx`（round 2 成果物、無改変で配置済み。
  バイト単位で複写し SHA-256 一致・48,299バイト・改変ゼロを確認済み）。**これはレビュー専用の
  受け皿であり、出荷コードではない**（ADR-0003）。
- **本番の候補提案画面は既に実装され、L4 が緑である**（`TDR-CS-00`〜`08` の15件、skipゼロ）。
  したがって**契約上の振る舞いは本番側では既に満たされている**。
- **本番は TSX ではない。** 出荷コードは Django テンプレート＋素のクライアント側 JavaScript であり
  （bundler なし、ADR-0009・`ARCHITECTURE.md`）、候補カード・地図・再提案モーダル・エラー表示は
  すべてクライアント側 JS が生成する。**タタキがそのまま実装になるのではなく、developer が
  `meta/agents.md` §4 手順5 に従って「承認済み画面設計に忠実に実装する」**という関係である。

**この非対称から、下の §1 と §2 は性質がまったく違う。**

- §1（人間クリティーク・裁定）＝**設計そのものへの要求**。本番画面に反映されなければ意味がない。
- §2（タタキの不備）＝**レビュー用モックだけの誤り**。本番の振る舞いは既に正しい。
  **これらを「本番の不具合」と誤読して本番を触らないこと。** 逆に、タタキを参照して実装する際に
  **これらの誤りを本番へ持ち込まないこと**が要点である。

### ★ リスク（architect・人間へのエスカレーション）

タタキは TSX、本番は素の JavaScript である。**両者の間には翻訳が必ず入る。** `meta/adr/0021` が
繰り返し警告している劣化の主要経路は「誰かが再解釈して作り直すこと」であり、**この翻訳はまさに
その経路に該当する**。designer は実装コードを読まないため、翻訳をどう安全に行うか（あるいは
タタキと本番の対応をどう機械的に担保するか）を判断できない。**この論点は architect と人間に委ねる。**

## 1. 人間クリティークと裁定（実機レビュー、2026-08-06）

### C-1 「地図が下のほうにあるからスクロールするのがだるい」

**実測**（orchestrator が実機で計測。designer は実行手段を持たないため供給を受けた事実）:

| ビューポート幅 | レイアウト | 地図の位置 | 文書の高さ |
|---|---|---|---|
| 1440px | 2列（788px + 420px） | 右カラムに `position: sticky`（`top: 24px`、文書上端から261px）＝**スクロールなしで見える** | 1,856px |
| 730px | **1列に折り返し** | **カード3枚すべての下**に落ちる | 2,769px（ビューポート910pxに対し約3画面） |

**タタキの該当箇所**: `.tdr-main-layout`（`grid-template-columns: 1fr 420px`）と

#### ★ 人間の裁定（2026-08-06）

> 「面積配分は言う通り、**PC表示はOK**だけど、**スマホ表示だけ工夫したいね**、です。
> センスのある対応を期待します」

- **広い幅（PC表示）の面積配分——カードが主・地図が右 sticky——は承認された。** 現行の承認済み画面
  （地図が主・カード一覧が右の細い列）からの反転は、これをもって**承認済みの設計**となる。
  round 1 と round 2 が独立に同じ配分へ到達した結果が、人間の裁定でも支持された形である。
- **未解決として残るのは狭い幅（スマートフォン想定）の扱いだけである。** 現状の「1列に折り返して
  地図がカード3枚の下へ落ちる」が「スクロールがだるい」の実体である。
- **解き方の方式は指定されていない**（「センスのある対応を期待します」）。方式の考案は
  **developer の領分**であり（`meta/adr/0021`: 骨格を保つ限り操作感・細かいUIの洗練は自由）、
  designer は発案しない（`.claude/agents/designer.md`）。

#### 狭い幅で壊してはならないもの（契約由来。方式の指定ではない）

developer が方式を選ぶ際、次はいずれも契約が要求しており、狭い幅でも成立しなければならない。
**「解によっては契約改訂が必要になる」ものがあるため、着手前にこの節を読むこと。**

| # | 要求 | 出典 | 狭い幅で危ういパターン |
|---|---|---|---|
| N-1 | **地図が初期表示から存在する**。認証済みの初期画面の `present` に `candidate-map` が含まれる | browser-interface v0.2 `authenticatedInitialOutcome.present`、`browserActions.initialProposal.success.present` | タップして初めて地図を生成する遅延描画は、初期状態で `candidate-map` が存在せず**契約違反になりうる**（下の注意書き参照） |
| N-2 | **カード→マーカー、マーカー→カードの相互強調が両方向**に成立する | `TDR-CS-02`、`browserActions.selectCard` / `selectMarker` | 狭い幅で地図を畳むと、マーカーを選ぶ経路が消える |
| N-3 | **選択状態が保持される**（`data-selection-state=selected`、他はすべて `unselected`） | 同上 | hover 依存の実装（M-5 参照）はタッチ環境で成立しない |
| N-4 | **全カードに1対1で対応するマーカーが揃っている** | `mapObservations.markerSet`（every-candidate-card-has-exactly-one-marker-with-same-data-candidate-ref） | 狭い幅でマーカーを間引く・仮想化するのは不可 |
| N-5 | **地図の範囲が表示中の候補を見渡せる** | `TDR-CS-02`「地図は示されている店舗が見渡せる範囲になる」、`data-map-fit-state=displayed-candidates` | 狭い幅で1件にズームする、一部だけ見せる、は不可 |
| N-6 | **禁止された地図要素を足さない** | `forbiddenTestIds`: 基点マーカー・経路・現在地・徒歩時間・private-search-origin | 省スペースのために現在地や距離で代替しない |
| N-7 | **新しい操作を置くなら `allowedPurposes` に無い** | `unavailableControls`（`allCandidateScreenFormControlsMustDeclarePurpose: true`、`allowedPurposes` はカード選択／マーカー選択／再提案の開始・選択・送信・取消／サインアウト／パスワード変更のみ） | **「地図を開く／閉じる」トグルボタンは、この列挙に該当する purpose を持たない**。採用するなら**契約改訂＝人間の承認点**である |

**N-7 の帰結（developer への実務上の要点）**: 狭い幅の解は大きく2種類に分かれ、**契約への影響が違う**。

- **操作を増やさない解**（CSS だけで積み順・高さ・追従を変える、地図を常時見える帯にする、等）
  → **契約改訂は不要**。`meta/adr/0021` が言う「骨格を保つ限り自由な洗練」の範囲で進められる。
- **操作を増やす解**（地図の開閉トグル、タブ切り替え等）
  → **`allowedPurposes` の改訂が要る＝人間の承認点**。黙って進めず、契約改訂の要否を明示して
  人間の判断を仰ぐこと。

**注意（designer が確定できない点）**: N-1 の `present` が「DOM に存在すること」なのか「可視で
あること」なのかは、L4 の DSL 実装に依存する。designer は実装コードを読まないため確定できない。
**遅延描画・条件付きレンダリングを検討する場合は、着手前に architect / tester に判定を求めること。**

**測定幅についての事実**: 上の実測は 730px で行われている。実機のスマートフォンは CSS ピクセルで
おおむね 390〜430px であり、**より狭い幅では未計測**である。方式の検証はその幅でも行うこと。

### C-2 「「切り口」などの用語がカスタマー向けでない」

利用者は月1回のランチ会の幹事——ITの専門家ではない普通の会社員である。現在の画面は「切り口」を
中心語として組み立てられている。「再提案」「提案」も同種の語である。

**影響する現在の文言**（意味を保ったまま日常語に改める対象）:

| 現在の文言 | 意味 |
|---|---|
| 「別の切り口で再提案」（ボタン・モーダル見出し） | いまの候補が合わないとき、別の選び方で出し直す操作 |
| 「現在の切り口: ...」（見出しバッジ） | 表示中の候補がどういう選び方で選ばれたか |
| 「この切り口では候補が見つかりませんでした」 | その選び方に合う店が無かった |
| 「別の切り口を選んで、もう一度提案を作れます。」 | 別の選び方でやり直せる |
| 「その切り口では再提案できません」 | 選ばれた選び方が今は使えない |
| 「表示されている切り口から選び直してください。」 | 画面の選択肢から選ぶよう促す |
| 「別の切り口で探しています」 | 出し直しの処理中 |

**制約**: 振る舞いを変えない。言い換えの過程で**元の文が言っていない事実（空席・混雑・所要時間等）を
足さない**。Hot Pepper credit の固定文言と OpenStreetMap の帰属表示は**言い換えの対象外**（契約リテラル）。

**★ 契約接点（designer は判定しない。architect へ回す）**:

「切り口」は**承認済みの `contracts/candidate-search.feature` 本文に埋め込まれている**。
`When 幹事が「別の切り口で再提案」を選ぶ`（鉤括弧つきでコントロールのラベルとも読める）、
`Then 再提案に使える切り口が3つ以下のポップアップで示される`、および `TDR-CS-03` のシナリオ名。

判定が要る問いは1つ: **受け入れシナリオの業務用語と、UI に表示するコピーは別物として扱えるか。**

- **扱える**とすれば、シナリオは変えずに表示コピーだけを改められる。先例として ADR-0011 決定3 は、
  `TDR-CS-02` の「総席数が示される」という本文について「業務の言葉だけで書かれており、可視表示の
  整形方式に言及していない」と判定し、`.feature` を変更不要とした。
- **扱えない**（鉤括弧つきの語をコントロール名と読む）とすれば、シナリオ本文の変更が要り、
  **人間の再承認点**である（`meta/permissions.md`: AIによる契約ファイルの直接変更は禁止）。

**参考事実（designer が確認した範囲）**: `contracts/candidate-search-browser-interface.yaml` v0.2 は、
再提案の起点・ダイアログ・選択肢を **test id**（`candidate-reproposal-open` 等）で観測しており、
**可視ラベルの文字列を検証していない**。したがって表示コピーの変更が L4 の機械検証を壊すことはない
と読める。ただし**これは機械検証への影響の観察であって、契約本文の解釈の判定ではない。**

## 2. タタキ（モック）側の不備 — **本番へ持ち込まないこと**

以下はすべて `design-preview` の成果物内の誤りである。**本番の該当する振る舞いは L4 が緑であり、
既に正しい。** モック自体を直すかどうかは developer の判断でよいが、直さない場合は
**「モックのこの部分は本番の正しい振る舞いを表していない」ことを承知しておくこと**——今後この
モックを参照して実装すると、誤りを本番へ持ち込む。

| # | 不備 | タタキの該当箇所 | 正しい振る舞い（契約） |
|---|---|---|---|
| M-1 | **再提案後の並び順が逆**。再登場2件が先、初出1件が後 | 再提案後の候補配列（`isNew: false` が先頭2件） | `ordering: every-new-card-precedes-every-repeated-card`（browser-interface v0.2）、ADR-0008 決定2。**初出が先・再登場が後**。既表示候補を除外はしない |
| M-2 | **選んだ選び方と表示される提案が一致しない**。`PROXIMITY` 以外を選ぶと常に `CAPACITY_REFERENCE` の提案が出る。結果として**表示中の選び方が選択肢に残る**経路がある | `currentProposal` の `useMemo` が `PROXIMITY` かどうかだけで分岐 | `TDR-CS-03`「新しい提案は選んだ切り口の候補と地図を示す」「現在表示中の切り口は再提案の選択肢に含まれない」 |
| M-3 | **「再提案中」の状態が無い**。モーダルで選ぶと即座に置換される | 該当状態の実装なし | 承認済みコピー「別の切り口で探しています／前の候補へ追加せず、選んだ切り口の候補へ入れ替えます。」。**本番に中間状態があるかは designer には確認できない**（実装コードを読まないため）。architect / developer が判定すること |
| M-4 | **API の enum 値を画面に表示**（`現在の切り口: PROXIMITY`） | 切り口バッジ | 幹事に見せるのは `title` と `rationale` のみ。`kind` は `data-reproposal-kind` **属性**として扱う |
| M-5 | **選択が hover のみ**。カードもマーカーも `div` に `onMouseEnter`/`onMouseLeave` だけ。click も focus も無く、キーボード到達性が無い | カードとマーカーのイベント | `browserActions.selectCard`/`selectMarker` は選択が `data-selection-state=selected` として**保持される**ことを求める。**hover は保持されない**。現行の承認済み画面は click / hover / focus の3経路を持っており、この点は後退している。**C-1 の狭い幅対応（タッチ環境）では致命的になる**（N-3） |
| M-6 | **供給データの1文字破損**。紹介文が「季節 **of** 小鉢」（正: 「季節**の**小鉢」） | 候補 a の `description` | ブリーフが渡した原文どおり「季節の小鉢と温かい定食を中心にした、架空の食堂です。」 |
| M-7 | **`alert()` を使い、「（TDR-CS-04検証済み）」と自称する** | レビューコンソールの `TDR-CS-04` ボタン | 検証は L4 が行う。成果物が自分で検証済みと称さない |
| M-8 | **レビュー用の案内がプロダクト面に混入**（未認証画面に「※ サインイン操作はレビューコンソールを使用してください」）。加えて**ID/パスワードの入力欄を新設**している | 未認証画面 | ADR-0003 決定3（レビュー機構をプロダクト操作と視覚的・意味的に分離）。**認証画面は `TDR-AUTH` で契約・実装ともに確定済みであり、本スライスの設計対象外**。この描写を「認証画面をこう変える提案」と読まないこと |

## 4. 実装時に必ず維持する契約上の観測点

タタキを本番へ反映する際、**視覚設計とは独立に**次が必要である
（`candidate-search-browser-interface.yaml` v0.2）。タタキは設計成果物なのでこれらの属性を
持っていないが、**本番実装には必須**である。

| 観測点 | 要求 |
|---|---|
| test id 一式 | `candidate-proposal-content` / `candidate-concept-title` / `candidate-concept-rationale` / `candidate-proposal-cards` / `candidate-card` / `candidate-map` / `candidate-map-marker` / `candidate-provider-credit` / `candidate-reproposal-open` / `candidate-reproposal-dialog` / `candidate-reproposal-option` / `candidate-reproposal-submit` / `candidate-reproposal-cancel` / `candidate-no-results` / `candidate-proposal-problem` / `candidate-proposal-problem-guidance` |
| カード必須8項目のラベル | `labelObservation`: 全項目に**可視 or アクセシブル**な非空ラベル。タタキは `genre` と `description` に可視ラベルを持たないが、**不可視のアクセシブルラベルと `data-field-label` で満たせる**（見た目を変えずに対応可能。**契約改訂は不要**） |
| 欠損表現 | `data-value-state` = `provided` / `unavailable` |
| 総席数 | ADR-0011。可視値は `38席` のような整形を許すが、**同一要素に `data-raw-value="38"`** を持たせる。タタキは数値と単位を別要素に分けているため、**どの要素が担い手かを実装時に決めること** |
| 再登場の識別 | `data-repeat-status` = `new` / `repeated`、`data-provider-page-href` |
| 選択状態 | `data-selection-state` = `selected` / `unselected`（カードとマーカーの両方。M-5・N-3 参照） |
| 問題状態 | `data-problem-code`（**属性であって可視テキストではない**。M-4 と同じ原則） |
| 地図 | `data-map-fit-state=displayed-candidates`、`data-map-tile-provider=openstreetmap-standard`、`candidate-map-attribution` |
| 置いてはならない操作 | `allowedPurposes` 外の form control を置かない（絞り込み・並べ替え・範囲指定・条件変更つき再試行など。**狭い幅対応で足す操作もここに掛かる。N-7 参照**） |

**未解決（前スライスからの持ち越し）**: 契約は再提案の `option` と `submit` を**別要素**と定めるが、
現行の承認済み画面もタタキも**選択肢のクリックが即再提案**である。本ラウンドが持ち込んだ差ではない。
**architect へ引き継ぐ。**

## 5. 変更してはならないもの（劣化防止）

- **公開リポジトリ境界**: 実座標・実地名・実店舗・provider レスポンス/ID/画像・資格情報・
  キー入りURL・数値距離を置かない。合成データは「架空」で始まる名前を保つ（ADR-0002・0003）。
- **privacy 境界**: 検索基点・基点マーカー・経路・現在地・徒歩時間を表示しない。地図に出るのは
  候補店舗だけ。非公開である旨の注記は可だが、**その地点が何であるかに言及しない**（ADR-0005 決定6）。

  価格・支払方法・特定日の営業判定・保存された嗜好。判定の目安は「API から返る7つの値だけで

- **主要ブロックの存在**: ヘッダー／現在の選び方の見出し＋出し直しの起点／地図＋カード一覧／
  出し直しモーダル／credit を含むフッター。**存在を消す改修は骨格の変更**であり人間承認を要する。
  狭い幅で地図の**見せ方**を変えることと、地図を**無くす**ことは別である。
